A-1 建部署目錄並放入 compose

🖥️ 在哪執行: Cats VM(ssh 進去)· 工作目錄 /opt

sudo mkdir -p /opt/cats-inbox
sudo chown "$USER":"$USER" /opt/cats-inbox

⚠ A-1 之後還不能跑 docker compose config —— 目錄裡還沒有 compose 檔,
它會回 no configuration file provided: not found。那兩行驗證在 A-3 之後。
(2026-08-28 實測:這個順序真的會被搞混,因為兩者都在 A 段裡。)

🔴 不在正式機 git clone(平台紅線:部署是改 tag 後 pull,不在正式機
git pull && build)。但也不要手貼 compose 的內容 ——

🔴 docker-compose.yml 裡有 ${POSTGRES_DB} 與 $${POSTGRES_USER}。
用未加引號的 heredoc 貼會被 shell 展開:${…} 變成空字串、
$$ 變成 shell 的 PID —— 檔案看起來還像 YAML,而 pg 起不來,
而錯誤訊息不會提到「你貼壞了」。

改成從 tag 抓那兩個檔(只抓兩個檔,不是 clone repo):

🖥️ 在哪執行: Cats VM(ssh 進去)· 工作目錄 /opt/cats-inbox

B=https://raw.githubusercontent.com/fttp0165/Cats_inbox/v0.1.1
curl -fsSL "$B/docker-compose.yml" -o docker-compose.yml
curl -fsSL "$B/.env.example"       -o .env          # 之後就地填三個值
grep -n 'cats-inbox-api:' docker-compose.yml        # 🔴 必須看到 image: …:0.1.1

🔴 URL 釘的是 tag v0.1.1,不是分支。 釘分支的話,compose 會跟著 main
往前走,而映像停在你部署的那一版 —— 兩者不一致而沒有任何錯誤訊息
(這正是第八條4 在講的同一件事,只是換到部署面)。
✅ 2026-08-28 實測:兩個 URL 皆 HTTP 200,且 tag 上的 compose image 就是 0.1.1。

📄 編輯哪個檔: /opt/cats-inbox/.env(A-1 已從 .env.example 抓下來)

要填的其實是四處,不是三個 —— 🔴 第 4 處是 2026-08-28 首次部署才發現的:

⚠ 症狀指錯方向:健康檢查刻意不查 DB,所以容器 healthy、/inbox/health 回 200,
而 B-3 的 alembic upgrade head 才失敗於
password authentication failed for user "cats_inbox" —— 看起來像 migration 的問題。
✅ 已加守門 test_env_example_db_url_carries_a_password_slot,.env.example 改為佔位字串。
⚠ 從 tag v0.1.1 抓下來的 .env.example 仍是舊的那一行 —— 這一處要手改
(下面的腳本會一併處理)。

🔴 順序:client secret 若曾外流,先輪替再填

輪替之後交付檔才是新值,而下面的腳本是從交付檔讀的 ——
反過來做的話,輪替完還要把 A-2 再跑一次。

🔴 四處都用「不印出來」的方式寫入

「不貼聊天/工單」(其建立腳本 2026-07-27 的教訓:secret 一律不印畫面)。

🏷️ 動到誰的東西: cats-portal 的交付檔(唯讀,不改它)

sudo python3 - <<'ENVFILL'
import os, re, pathlib
SRC = pathlib.Path("/opt/cats-portal/idp/.env.keycloak.cats-inbox")
ENV = pathlib.Path("/opt/cats-inbox/.env")

# ① client secret:自交付檔取,全程不印
m = re.search(r'^INBOX_OIDC_CLIENT_SECRET=(.+)$', SRC.read_text(), re.M)

               'INBOX_OIDC_CLIENT_SECRET=' + m.group(1), t, flags=re.M)

# ② 兩個亂數 —— 🔴 用 hex 不用 base64(理由見下)
pw = os.urandom(24).hex()
t, n = re.subn(r'^POSTGRES_PASSWORD=.*$', f'POSTGRES_PASSWORD={pw}', t, flags=re.M)

t, n = re.subn(r'^INBOX_SESSION_SECRET=.*$',
               f'INBOX_SESSION_SECRET={os.urandom(32).hex()}', t, flags=re.M)
assert n == 1

# ③ 🔴 同一個密碼也要寫進連線字串(第 4 處)
t, n = re.subn(r'^INBOX_DB_URL=.*$',
               f'INBOX_DB_URL=postgresql://cats_inbox:{pw}@cats-inbox-pg:5432/cats_inbox',
               t, flags=re.M)
assert n == 1
ENV.write_text(t)
print("✅ 四處已寫入,值全程未印出")

🔴 密碼用 hex 不用 base64。 base64 會產生 /,而這個值要出現在連線字串的
user:密碼@ 位置 —— / 在那裡會被當成路徑分隔,而症狀又是一個看不出原因的連線失敗。

⚠ INBOX_OIDC_INTERNAL_BASE 必須逐字等於交付檔裡那一行(http://keycloak:8080/auth,
不含 /realms/…)。填錯會組出 /realms/sporton/realms/sporton → discovery 404,
而離線測試全綠,只在第一個真人登入時出現(T04 記過)。

chmod 600 /opt/cats-inbox/.env
sudo python3 - <<'ENVCHK'
import re, pathlib
p = pathlib.Path("/opt/cats-inbox/.env"); t = p.read_text()
ok = True
need = ("POSTGRES_PASSWORD", "INBOX_SESSION_SECRET", "INBOX_OIDC_CLIENT_SECRET")
filled = 0
for k in need:
    m = re.search(rf'^{k}=(.*)$', t, re.M)
    if m is None:
        print(f"❌ {k} 這一行不存在"); ok = False
    elif not m.group(1):
        print(f"❌ {k} 是空的"); ok = False
    else:
        filled += 1
print(f"有值的 secret:{filled} / {len(need)}")
m = re.search(r'^INBOX_DB_URL=(.*)$', t, re.M)
if m is None or not re.match(
        r'postgresql://cats_inbox:[^@]+@cats-inbox-pg:5432/cats_inbox$', m.group(1)):
    print("❌ INBOX_DB_URL 沒有密碼或形狀不對"); ok = False
else:
    print("✅ INBOX_DB_URL 形狀正確(帶密碼)")
n = len(re.findall(r'^(?:INBOX_|POSTGRES_)', t, re.M))
print(f"變數行數:{n}(期望 14)")

grep -c '^KEY=$' 回 0 同時符合兩件事:①三個都填了 ②那三行根本不在這個檔裡。
⚠ 2026-08-28 實測就遇到一次「回 0 而被判讀成填好了」——
是同一次的另一個 grep 也異常回 0,才讓人去查;否則那個假通過會直接放過。
這與本專案記過三次的形狀相同:斷言的粒度比它宣稱保護的性質粗。

⚠ 14 是對的。 本稿 v1.5 之前寫「期望 13」是數錯了 ——
.env.example 有 14 個 INBOX_/POSTGRES_ 變數(COMPOSE_FILE 不符那個 pattern)。
🔴 .env 的內容一律不印:上面的檢查只輸出布林、計數與形狀判定。
