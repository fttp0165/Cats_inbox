## 1. 背景、上游與選址變更

### 1.1 這個系統是什麼(沿用設計規劃 v1.3 §1)

| 類型 | 說明 | 納入 |
|---|---|---|
| 系統通知 | 工單指派、TRF 退回、審核待處理等流程事件自動通知 | ✅ 階段一(M5 開通) |
| 公告 / 廣播 | 管理員發全站公告(維護通知、政策更新) | ✅ 階段一(M3–M4 先上線) |
| 人對人站內信 | 同事互寄訊息、對話串 | ✅ 階段二(M6,前置 DI-3) |
| 即時聊天 | 已讀狀態、線上狀態、WebSocket 推送 | ❌ 不做(CP 值低,沿用 v1.3 結論) |

設計規劃 v1.3 的關鍵前提「需要統一身分(SSO)」**已成立**:IdP(Keycloak realm `sporton`)已上線,upload-program、sporton_core、portal-admin 三個 App 已端到端接入(SSO 契約 §9 登記表)。收件人自始採 `sub`,不需任何帳號對應表。

### 1.2 選址變更(DI-1,已定)——本計畫的第一個決策

設計規劃 v1.3 §2 當時選「掛 compliance_system(新增 notifications app)」,並把「獨立通知微服務」標為「未來再議」。**2026-08-15 Benny 指示成立獨立 repo `Cats_inbox`,在 cats_portal 服務下提供站內通訊——「未來」已到,本計畫書據此改為獨立服務。**

變更理由(記錄下來,供日後檢視這個決策):

1. **compliance_system 仍在開發中**(portal 憲法系統清單現況欄)。把全平台的訊息中心綁在一個開發中系統的發版節奏上,通知的可用性會被 compliance 的迭代綁架;選址變更後 compliance **零配合工作**,反而卸下了原方案加在它身上的「訊息中心」角色。
2. **訊息中心天生是入口級服務**:所有系統都推事件進來、入口首頁的鈴鐺打它的 API。獨立的生命週期與回滾邊界,符合平台「各系統獨立 repo/容器、互通一律 HTTP API」紅線。
3. 當時反對獨立服務的理由是「**對單人維運過度設計**」。緩解:技術棧刻意極簡(FastAPI + PG15,無 Redis、無佇列、無 WebSocket,輪詢不推播),部署形態照抄 upload-program 已驗證的模式(同為 FastAPI 獨立服務、confidential client、子路徑掛載)。
4. **退路保留**:資料模型與 API 契約沿用設計規劃 v1.3 §4–§5 原案。若獨立維運被實測證明過重,併回 compliance 的遷移成本=搬四張表+改 upstream,原案隨時可退。

🔴 **回寫義務(憲法第二條5 同型):** 選址是設計規劃 v1.3 的實質內容,變更必須回寫該文件並升版,不得讓 portal repo 留著已知過期的選址結論——列為 **T02**(cats-portal 側 PR,由本專案發起、portal 收錄)。

### 1.3 與 portal 各交付物的關係

## 2. 上位契約對齊(cats-inbox 的落點)

### 2.1 SSO 接入(《帳號系統接入契約》**v3.3**;✅ **逐條對齊已完成**,見 `docs/契約對齊盤點_v3.3.md`)

| 契約義務 | cats-inbox 落點 |
|---|---|
| client 型別(§5.1) | **confidential + PKCE**(第一列:後端接 callback 換 token 的伺服器端應用) |
| redirect URI(§4.1) | `https://catsapp.sporton.com.tw/inbox/oidc/callback/`——⚠ 子路徑前綴必須含,§4.1 已載明照舊字面登記會漏掉、且只在登入當下才發現 |
| session 形態聲明(§10.2,申請必填) | **cookie / 伺服器 session** → front-channel logout 端點為 **MUST** |
| SLO 端點(§10.3) | `GET /inbox/oidc/frontchannel-logout`:免認證、冪等、只准刪 cookie、回 204、`iss`/`sid` 帶與不帶都要能處理 |
| 伺服器端算繪陷阱(§3.3) | access token 300s、SSO session 10h:**伺服器端必須以 refresh_token 主動續期**,否則登入 5 分鐘後靜默變未登入;測試替身不得抹平過期行為 |
| 容器內端點(§2.4) | 伺服器端走內部位址(`OIDC_INTERNAL_BASE`),**`iss` 維持對外網址不改** |
| token 驗證(§3.2) | RS256 only;JWKS 快取 1h、支援 kid 輪替;驗 `iss`/`aud`(=client_id)/`exp`;±30s;驗失敗 401、未開通 403 |
| 身分落地(§4.2) | 本地 user 表只存 `sub` + 本地角色;`name` claim 可能不存在,一律 fallback 到 `sub` |
| 首登(§4.3) | 自動建 user → **自動授 `reader`**(DI-2 已核可,僅自我範圍讀取);其餘業務功能 403 待開通頁,**頁上顯示本人 `sub`**(雞生蛋解法);bootstrap 管理員清單**每次登入比對**、idempotent、disabled 不復活。⚠ **v1.2 更正**:本列原寫「零角色」,與 §2.3-3 的「已核可」矛盾——**拿本節當規格的人會做出錯的實作**(同型漂移契約 v2.10/v3.2 都修過) |
| 同源義務(§4.10) | cookie `Path=/inbox/` + HttpOnly + SameSite=Lax;CSP `default-src 'self'` + nonce;base path=`/inbox/`;**零外部 CDN**(Bootstrap 自行託管);token 不進 localStorage |
| 停用能力(§1.1/D9) | inbox 本地角色可單獨停用;不把「這個人還能不能用」唯一押在 IdP 帳號狀態 |
| 註冊/密碼(§4.8) | 全部指向 IdP 內建流程;本服務零註冊頁、零密碼欄 |
| 帳號紀律(§6 通用建議) | 開啟 OIDC 後**不從自己後台手建人員帳號**(避免同一人兩列);本地不留 break-glass 帳號——鎖死風險由 §4.3 的 bootstrap 清單機制承擔 |

### 2.2 gateway 對齊(《App服務對齊指南》v1.3)

| 指南要求 | cats-inbox 落點 |

### 2.3 契約缺口(誠實列出——這三件事現行契約沒有給路,不得假裝已解)

1. **人對人寄件人顯示名稱(擋階段二,DI-3)。** ⏳ **2026-08-18 portal 回覆:不現在裁決**,俟本專案 **M4 上線後**與 rf-workorder #14 併案評估(理由:它要新增契約條文,而在資訊最少時定會定出比需要更寬的條文,**寬的條文收不回來**)。我方提案方向已依契約 v3.1 的判準修正為「**另立一節**」而非「§4.2a 增訂級別」——因同儕可見是**第三種失敗模式**(錯了不會被管理員或寄件端發現,而是被平台上另一個人看到)。
   **以下為原始論證,保留備查:**§4.2a L1 允許快取 `name`,但明文「**僅供管理後台顯示;不出現在一般使用者可見頁面、不進 API 回應**」——收件匣對一般使用者顯示寄件人姓名**不在現行契約允許範圍**,而只顯示 `sub` 的站內信沒有可用性。階段二動工前必須向 portal 送申請取得裁決(援 upload-program「申請書→裁決文件」前例;§4.2a 自己也預告了重開條件:「第二個 App 出現同樣需求,那就不是特例,而是本條需要重新設計」——cats-inbox 就是那個第二個 App)。提案方向見 §5 DI-3。**未裁決前,M6 不動工;階段一(系統通知+公告)刻意設計成零人名需求**(§3.6)。
2. ~~**S2S 憑證(擋系統通知推送,M5)**~~ → **已改變性質(2026-08-18 更新)**。
   🔴 **原敘述「S2S 章節未定稿」已失效**:章節早在契約 **v3.0(2026-08-15)** 就定稿為 **§11**。
   真正擋住 M5 的是 **§11.7 的一條既存禁令**:「**寫入型 S2S 一律不核發**」——而本服務的推送 API 正是寫入型(各系統把通知**寫進**我們)。
   **這兩者在計畫書上長得一樣,在排程上完全不同**:前者是等別人寫規格,後者是要一個裁決。
   ✅ **2026-08-18 已獲 portal 原則核可**(§11.7 第一案),規格已定:scope **`notification:push`**、
   必帶 `X-User-Id`(**須驗**形狀且不得等於呼叫方自身,否則 400)與 `Idempotency-Key`(去重)、
   `source_app` **一律由 service client 身分推導不得取自 body**、**逐端點驗 scope** 不只驗 `aud`。
   ⏳ 仍未有任何憑證核發——第一張要等**第一個來源系統(DI-4)立案**時照 §11 走。
3. **開通政策(DI-2)。** ✅ **2026-08-18 portal 核可**(附四條件,見 §5 DI-2 列)。以下為原始論證,保留備查。 契約 §4.3/4.4 的 deny-by-default 是 MUST:首登零角色→403 待開通。對 inbox 而言「讀自己的收件匣」是自我範圍資料(只能讀 `recipient_sub == 自己`),逐人手動開通=206 人排隊等著看通知,體感像壞掉(§4.2a D7-7 裁決自己也記載了這個代價)。**提案:讀自己收件匣+標已讀=首登自動授 `reader` 角色;人對人寄信、公告發布維持 deny-by-default 手動開通**(防自助註冊帳號濫發)。此為對契約 MUST 的偏離,需 portal/Benny 核可(前例:upload-program 首頁落地頁是「唯一經核准的偏離」,程序可循)。**未核可前照契約全 deny,不先斬後奏。**

## 3. 系統設計概要

### 3.1 架構

<!--SVG:cats-inbox_架構總覽-->

```
                        使用者瀏覽器
                             │ https(全 VM 只開 80/443)
                             ▼
              portal-gateway(唯一入口,portal 擁有)
        │           │            │                │
      /           /auth/       /inbox/ ★        /compliance/ /core/ /plm/ /upload/
        │           │            │                │
        ▼           ▼            ▼                ▼
   portal-      Keycloak    cats-inbox-api     各既有系統
   landing     (IdP/SSO)  (FastAPI,本專案)      │
        │                        ▲               │
        └── 每 30s 輪詢 ─────────┘◀── S2S 推送(client_credentials,M5)
            unread-count         │
     ═══ 以上皆在 external network cats-edge ═══
                                 │ inbox 內部網(不上 cats-edge)
                                 ▼
                        cats-inbox-pg(PostgreSQL 15,不曝 port)
```

三段資料流(沿用設計規劃 v1.3 §3):**① 事件來源**(各系統走 S2S、使用者/管理員走 JWT)推送 → **② cats-inbox** 存 → **③ 前端**輪詢顯示未讀鈴鐺與收件匣。

### 3.2 容器與網路

| 容器 | 內容 | 網路 | port |
|---|---|---|---|
| `cats-inbox-api` | FastAPI + Jinja2(伺服器端算繪),prebuilt image、non-root、健康檢查 `/inbox/health`(不查 DB)、restart policy | `cats-edge`(external)+ 自家內部網 | 只 `expose 8080`,不 publish |
| `cats-inbox-pg` | PostgreSQL 15(平台版本紅線),volume 持久化 | **只在自家內部網** | 不對主機發布 |

### 3.3 資料模型(沿用設計規劃 v1.3 §4,微調)

四張表,**皆只存 `sub`,無 email/姓名/密碼欄**(唯 `app_user.display_name` 為 §4.2a L1 快取,限管理後台顯示):

| 表 | 欄位要點 |
|---|---|
| `app_user` | `sub`(unique、不可變)、本地角色、`display_name`(nullable,L1 快取:僅自本人登入 token 寫入、附整批清除工具)、created_at、last_login_at |
| `message` | id(UUID)、`recipient_sub`、`sender_sub`(null=系統)、category(`system`/`direct`)、subject、body(**純文字**)、`action_url`(nullable,🔴 同站白名單)、`source_app`、`thread_id`(nullable,階段二)、is_read/read_at、created_at(後端產生,不信前端) |
| `announcement` | id、author_sub、title、body、audience(`all`;分群留待 N1)、starts_at/ends_at、created_at |
| `announcement_read` | announcement_id、user_sub、read_at(公告一則對多人,已讀逐人記,不逐人複製列) |

migration 用 Alembic;每條 migration 必附 backward,發版前本機 up→down→up 演練(憲法第八條6)。

### 3.4 API 契約(沿用設計規劃 v1.3 §5;實作時以 OpenAPI 為權威)

| 端點 | 認證 | 用途 |
|---|---|---|
| `POST /inbox/api/v1/notifications` | **S2S token**(M5 起) | 各系統推事件(recipient_sub、subject、body、action_url、source_app) |
| `GET /inbox/api/v1/notifications?unread=1` | 使用者 session/JWT | 我的訊息列表 |
| `GET /inbox/api/v1/unread-count` | 使用者 session/JWT | 未讀數(鈴鐺輪詢,30s) |
| `POST /inbox/api/v1/notifications/{id}/read` | 使用者 session/JWT | 標已讀(冪等) |
| `GET /inbox/api/v1/announcements/active` | 使用者 session/JWT | 目前有效公告 |
| `POST /inbox/api/v1/announcements` | 使用者 session/JWT + `announcer` 角色 | 發公告 |
| `POST /inbox/api/v1/messages` | 使用者 session/JWT + `sender` 角色 | 階段二:寄站內信(`sender_sub` 一律取自 token) |
| `GET /inbox/health` | 免認證 | 健康檢查,不查 DB |
| `GET /inbox/oidc/frontchannel-logout` | 免認證(§10.3) | SLO:清 session cookie、204、冪等 |

錯誤語意:401=token 無效;403=已認證未授權(含待開通);400=輸入不合法(含 action_url 非同站)。

### 3.5 權限模型(deny-by-default)

| 角色 | 能做什麼 | 授予方式 |
|---|---|---|
| (無角色) | 只有待開通頁(顯示本人 `sub`) | 首登自動建號 |
| `reader` | 讀自己的收件匣、標已讀、看有效公告 | ✅ **DI-2 已於 2026-08-18 核可**(附四條件):首登自動授,範圍寫死在自我範圍讀取;**可由本專案後台單獨停用**(C2);portal 得單方撤回 |
| `announcer` | 發公告、管公告有效期 | 管理後台手動 |
| `sender`(階段二) | 寄人對人站內信 | 管理後台手動(防自助註冊帳號濫發) |
| `admin` | 派角色、清 L1 快取、看來源系統登記 | bootstrap 清單(每次登入比對)+ 管理後台手動 |

鐵則:使用者只能讀 `recipient_sub == 自己 sub` 的訊息,查別人的回 403;`sender_sub`/身分欄位一律後端自 token 取,前端傳值不採信。

### 3.6 UI 原則

- 伺服器端算繪(Jinja2),base path `/inbox/`;Bootstrap 5 **自行託管**(對齊 portal Bootstrap5 導入方向,§4.10 禁 CDN);light 主題。
- body 純文字輸出、一律跳脫;`action_url` 僅同站(白名單驗證在寫入時就拒,不是輸出時才擋)。
- 🔴 **階段一 UI 零人名**:系統通知顯示 `source_app` 標籤(如「TRF 系統」),公告顯示「平台公告」——不顯示任何個人姓名,使 §4.2a 缺口(DI-3)不擋階段一。
- 待開通頁顯示本人 `sub` 與「找 inbox 管理員開通」指引(§4.3,不是冷 Forbidden)。

## 8. 對現有服務與資料的影響

- **全程 🟢 為主**:cats-inbox 是新增子路徑+新容器,不動任何既有系統的程式、容器、資料。compliance 因選址變更**卸下**原方案的工作,零配合項。
- **唯二 🟡**:T11/T12 的 gateway 路由新增與 reload——依部署形態紅線(低峰 + 容器內 `nginx -t` + 備份 + 秒級回滾),不得中斷 PLM/AES 正式站;landing 鈴鐺為 portal 側頁面改動,依 portal 憲法辦理。
- **本專案資料**:上線前無正式資料;上線後任何 migration 依共通紅線(備份+staging 雙向演練)。
