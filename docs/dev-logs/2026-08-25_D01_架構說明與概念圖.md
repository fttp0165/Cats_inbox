## 計畫段(動工前寫妥,第二條2)

### 🔴 這是計畫外的任務,先講清楚它的編號

任務表只有 `Tnn`(M0–M6 的施工任務),而本件是 Benny 直接指示的**文件交付**,
不屬於任何里程碑。編為 **D01**(D = 文件交付),並在任務表新增一節,
理由:第六條要求每個任務有日誌、第一條2 要求任務表反映狀態——
**一件做過的事不在任務表上,下次盤點就會以為它沒做過**。

### 目標

產出一份**給人看的**架構說明,涵蓋三件目前散落在各處的東西:

|---|---|---|
| **商業邏輯** | 上游設計規劃 §1/§3/§4 + 本 repo 的 A.3 紅線 + 十幾篇 dev-log | 沒有一份文件回答「這個系統在做什麼、為什麼這樣做」 |
| **技術架構** | `docs/開發計畫書.md` §3 + 既有的架構總覽 SVG | 有,但混在施工計畫裡 |
| **UI 概念** | **完全沒有**——只存在於四支模板與我的腦袋裡 | 上線前要讓人知道使用者會看到什麼 |

### 🔴 三條會被違反而沒有錯誤訊息的規矩

| 規矩 | 出處 | 落點 |
|---|---|---|
| 圖示一律**內嵌 SVG**、light、**零外部依賴**、單檔離線可開 | 憲法第四條5 | 三張圖都不得引用字型/CDN;`tests/test_docs.sh` 已有斷言 |
| md 與 HTML **不得漂移** | 第四條6 | HTML 由 `render_docs.py` 產生;新文件要**登記進 TARGETS**,否則 `--check` 不會看它 |
| 文件要有 metadata 與版本歷史 | 第七條 | 新文件要**加進 `test_docs.sh` 的清單**,否則守門看不到它 |

⚠ 中間那條是這次最容易漏的:**新文件不登記進 `TARGETS`,`--check` 會全綠**
——因為它根本沒去看那個檔。守門看起來在運作,而它只覆蓋了舊的那幾份。
(與 2026-08-24 在 portal 修的「函件守門只看單向」同型。)

### 影響範圍

🟢 **純文件。** 不動程式、不動資料庫、不動 portal、不動 VM。

### 驗收標準

1. `docs/架構說明.md` + `.html` 存在,且含 metadata 三行 + 版本歷史(第七條)。
2. 兩張新 SVG 存在,**light 主題、零外部依賴**;md 版以 ASCII 文字圖對應(第四條5)。
3. 新文件已登記進 `tools/render_docs.py` 的 `TARGETS` **與** `tests/test_docs.sh`
   的三份清單(md 存在 / HTML 存在 / 主題與外部資源)。
   🔴 這一條要**實際驗證守門有看到它**:故意改壞 md 之後 `--check` 必須紅。
4. 商業邏輯章節必須寫出**目前做不到的事**(群組定向、人名、推送),
   不得只寫「設計上會有什麼」——那會讓讀的人以為現在就有。
5. `bash tests/run_all.sh` 全綠。

### 回滾方式

純新增檔案 + 兩處清單登記。`git revert` 即可;無資料、無設定、無服務影響。

### 為什麼這樣做(關鍵決策)

**① 未實作的部分一律以虛線 + 灰字畫,不畫成已經有的樣子。**
兩張 SVG 裡的 S2S 推送、人對人寄信、入口鈴鐺都是虛線。
🔴 架構圖最常見的謊是「把設計畫成現況」——看的人不會去查哪一塊還沒做。

**② 商業邏輯專門開一節寫「現在做不到的三件事」**(§2.4)。
群組定向、顯示姓名、系統推送——各自寫出**為什麼做不到**與**要什麼才能開放**。
不寫的話,讀的人會以為現在就有,而那三件事都不會有錯誤訊息告訴他沒有。

**③ 兩張表相反的外鍵決定寫進架構說明,不只寫在 migration 註釋裡。**
`message.recipient_sub` 不設外鍵 / `announcement_read.user_sub` 要設——
這在日後看起來會像不一致,而**看架構說明的人不會去讀 migration**。

**④ `Dnn` 與 `Tnn` 分開編號。**
混編會讓里程碑完成度失真(文件做完了不代表功能做完了);
但仍必須列在任務表上,否則下次盤點會以為沒做過。

### 測試結果(紅 → 綠的證據)

**驗收第 3 項要求「實際證明守門看得到新文件」,已照做:**

```
故意在 docs/架構說明.html 尾端加一行 → render_docs.py --check
  ✅ 守門看得到新文件(--check 紅)
還原 → --check
  ✅ 還原後 --check 綠
```

**綠:** `bash tests/run_all.sh` → 文件層 **45 過 / 0 敗**(登記前 40)、
pytest **85 passed**,合計 **130 項全綠**。

**SVG 檢查:** `docs/架構說明.html` 內嵌 **3 張 SVG**、外部資源 **0**。

### 🔴 一項發現

**新文件不登記進 `TARGETS`,`--check` 會全綠。**
它不是「檢查通過」,是**根本沒去看那個檔**。
本次因為驗收第 3 項明文要求「故意改壞一次」才確認守門真的覆蓋到它——
⚠ 而如果只看「跑完是綠的」,結論會完全相反。

這與 2026-08-24 在 portal 修的「函件守門只看單向」是同一個形狀:
**守門存在、看起來在運作、而它只覆蓋了一部分對象。**
兩次都不是規則寫錯,是**清單沒有跟著新增的對象一起長**。

💡 後續建議:`test_docs.sh` 的三份清單目前是**手寫的**。
可以改成掃 `TARGETS` 自動產生,讓「新增文件」與「納入守門」變成同一件事
(比照 portal 的 `run-all.sh` 用自動探索取代逐支列出)。列為建議,本次不做——
那會動到守門本身,而動守門要有自己的紅測試。

### 對現有資料的實際影響

### 遺留問題與後續建議

1. **架構說明會過期。** §6「現在做到哪」那張表在 T09–T12 完成後就不對了。
   ⚠ 建議把它併入第六條的回寫義務:**M3/M4 完成時同批更新**,
   否則它會變成一份「看起來很完整而內容過期」的文件——正是 portal 憲法
   v1.17 那條規則要治的病。
2. 💡 `test_docs.sh` 的清單改為自動探索(見上方發現)。
3. ⚠ 兩張新 SVG **沒有測試釘住它們的內容**,只驗了「檔案存在、無外部依賴」。
   圖畫錯了(例如把虛線畫成實線)不會有任何東西發現。目前接受這個限制:
   圖的正確性靠人看,而它不像設定值那樣會被「順手改掉」。
