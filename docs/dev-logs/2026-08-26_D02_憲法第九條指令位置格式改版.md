## 計畫段(動工前寫妥,第二條2)

### Benny 指示的新格式(逐字)

```
> 🖥️ **在哪執行:** WSL(Ubuntu)· 工作目錄 ~/upload-program-
> 🖥️ **在哪執行:** Cats VM(ssh 進去)· 工作目錄 /opt/upload-program
> 📄 **編輯哪個檔:** /opt/upload-program/docker-compose.yml
```

⚠ 三行是**三種行型的範例**(兩種「在哪執行」+ 一種「編輯哪個檔」),
不是三行併用。

### 這次改的是什麼、以及它比舊格式多了什麼

| | 舊(第九條11,v1.1 起) | 新(本次) |
|---|---|---|
| 形狀 | 指令區塊前一行 `【機器】【路徑】【專案】` | `>` 引言區塊,`🖥️ 在哪執行` /(必要時)`📄 編輯哪個檔` |
| 欄位 | ①機器 ②路徑 ③專案 | 平台 + 工作目錄;**要改哪個檔另外一行** |
| 🔴 **新增的能力** | — | **「要改哪個檔」有自己的一行,而且是完整路徑** |

🔴 **「編輯哪個檔」這一行是舊格式沒有的,而它補的是一個實際的缺口:**
舊格式只標了「指令在哪個工作目錄下」。要改檔案時,檔名是**藏在指令裡**的
(例 `$EDITOR app/__init__.py`)—— 相對於哪個目錄要讀的人自己推,
而**推錯不會有錯誤訊息**:他會改到另一個 repo 裡同名的檔,
測試照樣綠(改的那份沒有進部署),或是新建一個空檔案。
`docs/發版SOP.md` §1 目前就有三處這種寫法。

### 🔴 一個不能在改版中丟掉的東西:「動到誰的東西」

舊格式的第三欄「③專案」不是冗餘。本專案 A.4 明載**最容易貼錯的一組**是:

```
docker exec portal-gateway nginx -s reload
```

它在 **VM** 上執行,而動的是 **portal 擁有的** gateway ——
🔴 **這個指令的「工作目錄」根本不重要,而「動到誰的東西」是全部的重點。**
新格式若只有「平台 + 工作目錄」,這個資訊就沒有地方放了。

→ 處置:新增 **第 13 款**,要求「指令動到的東西不屬於該工作目錄的專案時,
必須另標一行 `🏷️ 動到誰的東西`」。
⚠ 依第九條自己的規矩 **往後加,不插隊**(插隊會讓既有引用悄悄指到別的東西)。

### 為什麼這樣做(關鍵決策)

**① 「📄 編輯哪個檔」獨立一行,而不是讓檔名留在指令裡。**
`$EDITOR app/__init__.py` 把檔名藏在指令裡,**相對於哪個目錄要讀的人自己推**
——而推錯不會有錯誤訊息:他會改到另一個 repo 裡同名的檔(**測試照樣綠,
因為改的那份沒有進部署**),或憑空新建一個空檔案。
`發版SOP.md` §1 原本就有三處這種寫法,已全部改成完整路徑。

**② 新增第 13 款,而不是把舊格式的「專案」欄直接刪掉。**
`docker exec portal-gateway nginx -s reload` 的**工作目錄根本不重要**,
而它動的是綁 80/443、全 VM 唯一的 gateway ——
只有「平台 + 工作目錄」的話,這個資訊沒有地方放。
第 11 款標的是「我站在哪裡」,第 13 款標的是「我伸手碰的是誰的」。
⚠ 兩者一致時不必寫 —— 每個指令都貼一行反而讓人不看。

**③ 條文往後加,不插隊。** 第九條自己就寫著這條規矩
(插隊會讓既有引用悄悄指到別的東西)。11 款是**格式改寫**(同一款、同一件事),
13 款是**新增**,兩者都沒有讓既有編號位移。

**④ 既有文件分兩類處置,理由相反。**
**常設操作文件**(發版SOP)改寫 —— 有人會照著做,舊格式留著就是兩種寫法並存;
**歷史紀錄**(dev-logs、往來函件)不動 —— 竄改歷史比格式不一致更糟,
它們記的是「當時怎麼做的」。生效範圍沿 portal 第四條7 的先例。

**⑤ 守門分三行各自報錯,不合成一次 grep。**
合起來的話,少了其中一種標示時錯誤訊息只會說「格式不在案」,
而讀的人不知道少的是哪一個。
