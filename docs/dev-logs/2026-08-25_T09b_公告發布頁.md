## 計畫段(動工前寫妥,第二條2)

### 目標

讓有 `announcer` 的人**不必用 curl** 就能發公告:

1. `GET /inbox/announcements/new` — 表單(需 `publish_announcement` 能力);
2. `POST /inbox/announcements/new` — 送出,成功後 **303** 導回 `/inbox/`(讓他當場看到);
3. 收件匣頁在**有該能力時**顯示「發布公告」入口 —— 沒有入口的頁面等於不存在;
4. 四種 400 在畫面上各有**可讀的訊息**,且**保留使用者已填的內容**。

### 🔴 三件這次才會第一次遇到的事

**① 這是本專案第一個 POST 表單 —— CSRF 必須與表單同批做完。**
現有的 POST 都是 JSON API(同源 cookie + JSON body,跨站表單送不出 JSON)。
表單一出現,`<form>` 就可以從任何網站指向我方端點。
做法:token = **HMAC(session secret, session key)**,渲染成 hidden input,POST 時比對。

- 🔴 **必須是 HMAC(單向),不能用 `URLSafeSerializer` 簽章**——後者只是簽名不是加密,
  token 會**把 session key 明文帶到 HTML 上**,而那正是密封 cookie 在保護的東西。
- ⚠ session cookie 已是 `SameSite=Lax`,它本身就擋掉大部分跨站 POST。
  但 Lax 有已知缺口(舊瀏覽器、頂層 GET 導覽),而**CSRF 成功時沒有錯誤訊息**
  ——受害者只會看到一則自己沒發過的公告。兩層都要。

**② `datetime-local` 送出的值**不帶**時區,而我方 API **拒收不帶時區的時間**(T09)。**
也就是說照直接接會**每一次排程都 400**。
🔴 解法是**由頁面宣告時區**,不是讓伺服器猜:表單旁明寫「時間為台北時間(UTC+8)」,
後端把表單值補上 `+08:00` 再走**同一條**已驗證的路徑。

> **這不是放寬 T09 的規則,是兩件不同的事:**
> API 拒收是因為**呼叫方可能在任何時區,我方無從得知**;
> 表單可以補是因為**頁面已經告訴使用者這個欄位是什麼時區**——宣告不是猜。
> ⚠ 台灣**沒有日光節約**,所以用固定位移 `+08:00` 是精確的
> (換到有 DST 的時區時這個寫法會錯,故在程式註釋標明)。

**③ CSP 之下這一頁不能有任何 JavaScript,也不能有行內樣式屬性。**
`default-src 'none'` 且刻意沒有 `script-src`(T10)。
所以:不用 JS 補時區(見②)、不用 JS 做前端驗證、樣式一律 class。

### 驗收標準

1. **權限**:`announcer` GET 200;`reader` GET **403**;未登入 **401**。
2. **CSRF**:缺 token / 亂給 token / 用**別的 session** 的 token → **403 且零列寫入**。
3. **時區**:表單填 `2026-08-30T02:00`(台北)→ 存進 DB 的是 `2026-08-29T18:00Z`。
   🔴 這一條要斷言**實際的 UTC 值**,不是只斷言「發布成功」——差 8 小時時
   兩者都會成功。
4. **四種 400** 各自在畫面上有可讀訊息(空標題 / 無效時間 / 空窗 / 未知 audience),
   **且已填的標題與內容仍在表單裡**(否則使用者要重打一次)。
5. **入口**:`announcer` 的收件匣頁有連結;**`reader` 的沒有**
   (顯示一個點下去會 403 的連結比不顯示更糟)。
6. 成功後 **303** 導回 `/inbox/`,且那則公告當場出現在頁面上。
7. 頁面零外部資源、`<style>` 帶 nonce、**零行內樣式屬性**、light 主題。
8. `bash tests/run_all.sh`(起本機 PG)全綠 + 突變檢查逐項確認。

### 回滾方式

純新增(一支模板 + 一支 router + session 兩個方法)+ 收件匣頁一個 `{% if %}`。
`git revert` 即可;無 migration、無資料變更。
⚠ 回滾後公告仍可用 API 發布(T09 的端點不動),只是沒有畫面。

### 為什麼這樣做(關鍵決策)

**① CSRF token 用 HMAC(單向)且綁 session,不是簽章。**
用 `URLSafeSerializer` 之類的簽章做 token 會把 session key **明文(base64)
帶到 HTML 上** —— 而那正是密封 cookie 在保護的東西(token 會落在頁面、
referer、快取、螢幕截圖裡)。綁 session 則是為了讓攻擊者在自己 session
拿到的合法 token **打不到**受害者的請求。

**② 表單時間由頁面宣告時區,不由伺服器猜。**
`datetime-local` 送出的值不帶時區,而 T09 的 API **拒收**不帶時區的值。
解法是頁面明寫「台北時間(UTC+8)」,後端補上位移再走**同一條**驗證路徑。
🔴 這不是放寬 T09:API 拒收是因為「呼叫方可能在任何時區,我方無從得知」;
表單可以補是因為「頁面已經告訴使用者這個欄位是什麼時區」——**宣告不是猜**。
位移由 `FORM_TZ` 算出,不寫死字面 `+08:00`(兩處寫同一件事,改一個忘一個
不會有錯誤訊息,只會差幾小時)。

**③ 驗證+建立抽成一處(`_validate_and_create`),API 與表單共用。**
各寫一份的話兩邊會漂移,而**漂移之後寬的那一邊贏** —— 攻擊者只會走那一邊。

**④ 成功回 303 而不是 200。**
留在 POST 的結果頁上,使用者按重新整理就會**再發一則公告**。

**⑤ 入口連結只在真的有能力時顯示。**
顯示一個點下去會 403 的連結**比不顯示更糟** —— 它讓人以為自己做錯了什麼。
(反向也要測:永遠不顯示的話 `announcer` 找不到這一頁。)

文件層 **45 過 / 0 敗**、pytest **164 passed / 0 skipped**,合計 **209 項全綠**。

**突變檢查:19 項全被抓到** —— ⚠ 但這是**修掉三個測試洞之後**的數字,見下。

### 🔴 三個測試洞,全部由突變檢查找出來

第一輪 19 項有 **3 項沒抓到**,而三個都是**我的斷言寫錯**,不是工具問題:

| 突變 | 為什麼逃掉 | 修法 |
|---|---|---|
| CSRF token 把 session key 直接串進去 | 我拿 `cookie.split(".")[0]` 當 session key 比對,而**那是 key 的 base64**,不是 key 本身 | 改用 `store.unseal(cookie)` 拿真正的 key;再加一條「token 必須是**純** 64 字元 HMAC 十六進位」 |
| 400 時清空表單 | 測試資料用「標題」「內容」當值,而那兩個詞**在 `<label>` 裡本來就有** → 「已填內容還在」永遠成立 | 值改成 `標題ZZQ7` / `內容XXR9`(不會出現在模板裡) |
| 400 時只寫「發布失敗」 | 我對**整頁**做 `re.search(欄位名)`,而那些詞在 label 裡本來就有 | 先抓出 `alert-danger` 那一塊,只在**錯誤框內**比對 |

🔴 **共同形狀:斷言的對象裡本來就含有我要找的字串。**
三個都會讓測試看起來很嚴格而實際上永遠通過 —— 而**只跑一次是綠的,
不會有任何線索**。這一輪是突變檢查第一次抓到**測試本身**的邏輯錯誤
(前幾輪抓到的都是量測工具的問題)。

⚠ 另有 3 項第一輪顯示「突變沒套用」——那是我在修訊息可讀性時改了那幾行,
sed 的目標字串跟著失效。改對後三項全紅。**守門的警示行有效**(T10 加的)。

### 遺留問題與後續建議

1. ⚠ **CSRF 只做在這一個表單上。** 目前只有這一個 POST 表單,但角色後台的
   「清除顯示名稱」按鈕(T05)也是 POST 表單 —— **它沒有 CSRF**。
   🔴 建議下一個任務一併補,並改成「所有 POST 表單一律驗 CSRF」的**列舉式守門**
   (比照 T10 的 CSP:逐處加會忘記,而忘記沒有症狀)。
2. ⚠ 表單沒有「預覽」。公告是一則對多人,發錯要靠改資料庫。
   目前接受這個限制(公告可設 `ends_at` 讓它自然失效),但值得列為後續。
3. 💡 `_humanize` 是字串前綴比對。欄位名一旦改,訊息會靜靜地退回英文欄位名
   ——不會壞,只是變得不那麼好讀。可考慮改成由驗證函式直接帶標籤。
