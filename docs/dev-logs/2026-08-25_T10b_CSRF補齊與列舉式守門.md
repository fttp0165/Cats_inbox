## 計畫段(動工前寫妥,第二條2)

### 🔴 這個洞不是新破的,是一直開著而沒有人注意到

T05 做角色後台時建了兩個 POST 表單:

| 路由 | 做什麼 | 現況 |
|---|---|---|
| `POST /inbox/admin/users/roles` | 派 / 停某人的某個角色 | ⛔ **無 CSRF** |
| `POST /inbox/admin/users/purge-display-names` | 清除顯示名稱快取(可整批) | ⛔ **無 CSRF** |

當時本專案還**沒有任何 CSRF 機制**,所以沒有「忘記加」這件事可言 ——
機制是 **T09b** 才建立的。也就是說:洞從 T05 就在,而
**T09b 做第一個表單時才浮現**。

🔴 **後果的量級要講清楚**:第一個表單能讓攻擊者**替自己開通任何角色**
(誘使管理員在登入狀態下開一個網頁即可),第二個能**整批清掉顯示名稱快取**。
兩者成功時都只是一個 303 導回清單頁 —— **管理員看到的畫面完全正常**。

### 目標

1. 把 CSRF 驗證抽成**一個共用相依**(`app/csrf.py`),取代 T09b 寫在
   發布頁 handler 裡的手動比對;
2. 兩個後台表單接上它(模板補 hidden input);
3. 🔴 **列舉式守門**:自動找出「所有接受表單的 POST 路由」,逐一驗證
   **沒帶 token 就 403**,而且**帶了 token 就不是 403** ——
   後者是防這支測試變成空檢查的那一半。

### 🔴 三件決定了做法的事

**① 守門必須是列舉式,不能逐支列出。**
逐支列的話,下一個新表單**不會被列進去**,而漏掉不會有任何症狀
——表單照樣送得出去,只是沒有 CSRF 保護。
與 T10 的 CSP 守門同一個形狀(那支列舉所有回 HTML 的路由)。

**② JSON 端點刻意**不**要求 CSRF,而這需要寫下理由。**
`application/x-www-form-urlencoded` 是 CORS 的「簡單內容型別」,
跨站表單**送得出去**;而 `application/json` 會觸發預檢,被 CORS 擋掉。
所以守門的判準是「這個路由收不收表單」,不是「這個路由會不會寫資料」。
⚠ 若日後有端點改成接受 `text/plain` 或 `multipart`,它也在風險內
——判準要跟著改,故寫進註釋而不只寫在日誌。

**③ 測試必須用「身上有全部角色」的人來打。**
不然 403 可能來自**沒有權限**而不是**沒有 CSRF**,而兩者的回應都是 403
——那會讓守門在權限判定壞掉時仍然全綠。
🔴 並且要驗**反面**:同一個請求**帶上正確 token 後不得再是 403**。
少了這一半,一個「所有表單 POST 一律 403」的實作也會讓守門全綠,
而後台**完全不能用**。

### 影響範圍

| 對象 | 影響 |
|---|---|
| 資料庫 | 🟢 **不動**。無 migration |
| 既有 API(JSON) | 🟢 完全不動(見決定②) |
| 既有 UI | 🟡 後台兩個表單各加一個 hidden input;發布頁改用共用相依(行為不變) |
| portal / VM / gateway | 🟢 不動 |

⚠ **一項使用者可見的行為變更**:後台頁面**開著超過 session 壽命**之後送出表單
會拿到 403(token 隨 session 失效)。這是正確行為,但訊息目前是 JSON
`{"error": "csrf_failed"}` —— 列為遺留問題。

### 驗收標準

1. **列舉式守門**:找出所有收表單的 POST 路由(≥3 支),逐一驗證
   ①無 token → **403**、②有 token → **不是 403**。
   🔴 並斷言「找到的路由數 ≥3」——找到 0 支時測試會全綠而什麼都沒驗。
2. 兩個後台表單:無 token 的 POST → 403 **且零副作用**
   (角色沒被改、快取沒被清)。
3. 發布頁改用共用相依後,T09b 的 17 支測試**維持全綠**。
4. CSRF 失敗時 log 有一行(只記 `actor` 與路徑,不記表單內容)。
5. `bash tests/run_all.sh`(起本機 PG)全綠 + 突變檢查逐項確認。

### 回滾方式

純新增一支 `app/csrf.py` + 三處接線 + 兩個模板加 hidden input。
`git revert` 即可;無 migration、無資料變更。
⚠ 回滾後後台表單可用但**沒有 CSRF 保護**(回到 T09b 之前的狀態)。

| `tests/test_csrf.py` | **新增 7 支**(含列舉式守門) |
| `docs/任務表.md`(v1.17)、`docs/TDD測試計畫表.md`(v1.11)、`docs/架構說明.md`+`.html`(v1.4) | 回寫 |

### 為什麼這樣做(關鍵決策)

**① CSRF 抽成一個相依,不留在各 handler 裡。**
T09b 把比對寫在發布頁的 handler,而後台那兩個表單**當時沒人想到**。
抽成相依之後,守門可以**列舉**所有收表單的路由逐一驗證,新表單自動被涵蓋。

**② 判準是「這個路由收不收表單」,不是「它會不會寫資料」。**
`application/x-www-form-urlencoded` 是 CORS 的簡單內容型別,跨站 `<form>`
**送得出去**;`application/json` 會觸發預檢而被擋掉。所以 JSON API 不需要 CSRF。
⚠ 若日後有端點改成接受 `text/plain` 或 `multipart`,判準要跟著改。

**③ 守門用「身上有全部角色」的人來打,而且兩個方向都驗。**
403 可能來自沒權限而不是沒 CSRF —— 兩者回應相同。給全部角色之後,
任何 403 就只能是 CSRF。而**帶了 token 不得再是 403** 這一半,擋的是
「所有表單 POST 一律 403」那種讓後台完全不能用的實作。

### 測試結果(紅 → 綠的證據)

**紅:** 新測試先寫,首次執行 **7 全部失敗**。
其中 `test_purge_without_csrf_has_no_effect` 的失敗訊息是 `assert 303 == 403`
—— 那一行就是「這個洞真的在」的直接證據:**沒有 CSRF 的整批清除當時是成功的**。

**綠:** `bash tests/run_all.sh`(**已起本機 PostgreSQL**)→
文件層 **45 過 / 0 敗**、pytest **171 passed / 0 skipped**,合計 **216 項全綠**。

**突變檢查:13 項全被抓到**(修掉一個測試洞之後,見下)。

### 🔴 三項發現

**① T10 的「列舉所有 HTML 路由」守門,實際上只驗到自動產生的文件頁。**
FastAPI 0.141 把 `include_router()` 的東西包成一個 `_IncludedRouter`,
`app.routes` 上**只看得到**文件路由加那一個包裝物。
那支測試斷言「至少檢查到 3 個 HTML 路由」,而**剛好**有 3 個文件頁是 HTML
(`/inbox/docs`、`/docs/oauth2-redirect`、`/redoc`),於是它一直全綠 ——
**`/inbox/`、`/inbox/pending`、`/inbox/logged-out/`、`/inbox/admin/users`
一個都沒驗到**。

🔴 這與 D01 的發現同型:**守門存在、看起來在運作,而它只覆蓋了一部分對象。**
⚠ 而 `_IncludedRouter` 這件事 **T06 已經記過一次**了(當時改用行為斷言繞過)
—— 這是它的第二個受害者。已建 `tests/conftest.py::iter_routes()` 統一處理,
並在守門裡補「必須列舉到 `/inbox/` 等三個真頁面」的斷言。

**② 列舉式守門會打到 `/inbox/logout`,而它會把 session 清掉。**
第一版照順序打每一個 GET 路由,而 logout 排在 `/inbox/` 之前 ——
後面的頁面全變成 401(不是 HTML),於是**被靜靜地跳過而測試是綠的**。
改成**每一支之前重新登入**,比維護一份「哪些路由有破壞性」的清單可靠
——清單會忘記跟著新路由長。

**③ 加這道保護時,我把 401/403 的分界弄壞了。**
第一版把「沒有 session」也當成 CSRF 失敗而回 403,於是**未登入的 POST
從 401 變成 403**,呼叫方會以為自己是「登入了但沒權限」。
抓到它的是 **T09b 留下的 `test_unauthenticated_is_401`** ——
這是「既有測試當安全網」(第三條4)真的發揮作用的一次,值得記下來。

⚠ 另有一個測試洞由突變檢查抓到:`test_admin_page_has_csrf_in_every_form`
原本只驗 `name="csrf_token"` **在不在**,所以把傳給模板的 token 改成空字串
之後它仍然綠 —— 而那會讓**每一次送出都 403、後台完全不能用**。
已改成同時驗值是 64 字元的 HMAC 輸出。

### 對現有資料的實際影響

🟢 **無。** 無 migration、無欄位變更。
⚠ 一項**行為**變更:後台頁面開著超過 session 壽命後送出表單會拿到
`403 csrf_failed`(token 隨 session 失效)。這是正確行為。

### 遺留問題與後續建議

1. ⚠ **CSRF 失敗時使用者看到的是 JSON `{"error":"csrf_failed"}`**,不是一個
   「請重新載入頁面」的畫面。表單越多這個體驗越糟,建議在 T12 前補一個
   簡單的錯誤頁(現在只有兩個表單,還撐得住)。
2. ⚠ `iter_routes()` **依賴 FastAPI 的內部結構**(`_IncludedRouter.original_router`)。
   升版可能失效 —— 防線是每個用它的測試都斷言「找到的數量 ≥ N」**且**
   「這幾個已知路徑必須在裡面」,結構一變就會紅,而不是靜靜地變成空檢查。
3. 💡 目前只有最外層的 router 前綴需要手動補(內層的已寫進葉節點)。
   這個不對稱是 FastAPI 的實作細節,已寫進 `iter_routes` 的註釋。
