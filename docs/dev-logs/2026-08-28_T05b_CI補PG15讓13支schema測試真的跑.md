```
#    ——那不是覆蓋,是沒測。不講出來的話,「全綠」會被讀成「都驗過了」。
```

腳本在它自己的輸出裡防住了;而**沒有任何東西防住「有人把那句話抄進文件時把條件丟掉」**。

### 為什麼這樣做

#### 🔴 這一條的起點是「只想改一個過期的數字」

進度表 §5 寫著「pytest **183 passed / 0 skipped**」,而我知道加了兩條守門之後應該是 185。
去跑一次取真數字 —— 看到的是 `172 passed, **13 skipped**`。

那 13 項的存在**本來就寫在同一張表的下一列**:

> `| ⚠ 需真 PostgreSQL 的 migration 測試 | 13 項 —— 沒起本機 PG 時它們是 skipped … |`

**兩列互相矛盾,而矛盾撐了很久。** 第一列宣稱 0 skipped,第二列說明什麼情況下不是 0,
而第一列沒有把自己成立的條件寫出來。

🔴 **但真正被漏掉的不是那個矛盾,是一個沒有人問的問題:「CI 屬於哪一種?」**
第二列老實寫著「沒有真 PG 時會 skip」,而**從來沒有一列去問 CI 有沒有真 PG**。
答案是沒有 —— `.github/workflows/ci.yml` 從 T01 起就沒有 `services:` 區塊,
於是那 13 支(schema 與 migration 的測試,**含共通紅線要求的 up→down→up 雙向演練**)
**在 38 次 CI 上一次都沒有跑過**,而第三條2 的名字就叫「納入 CI 防止回歸」。

⚠ **skip 不是失敗,綠燈仍然是綠燈。** 這是它撐那麼久的全部原因。

#### 🔴 發現①:錯的理由寫在測試檔的檔頭上

`tests/test_skeleton.py` 的 module docstring 原本寫:

> 為什麼是靜態斷言而不是 `docker compose up`:這些錯誤全部在**檔案內容**就決定了,
> **而 CI runner 上跑不起真的 PostgreSQL+gateway。**

`gateway` 那半是對的(CI 上沒有整個平台可以反代)。
**`PostgreSQL` 那半是錯的** —— GitHub Actions 的 `services:` 就是用來跑它的。
而錯的那半**正是有影響的那半**。

🔴 **一個寫下來的錯誤理由比沒有理由更難發現 —— 它讀起來像已經有人判斷過了。**
沒有那句話的話,「CI 要不要有 PG」還是一個開著的問題;有了它,那個問題看起來已經結案。
⚠ 這與本專案記過的「守門存在、看起來在運作、只覆蓋一部分對象」是**姊妹形狀**:
那些是**保護**不完整,這一個是**判斷**不完整,而兩者都因為「看起來已經處理過」而不被複查。

已在原處逐字更正並標明日期與原因(不刪掉原句 —— 讀的人要看得到當初錯在哪)。

#### 🔴 發現②:skipif 的粒度比 fixture 實際需要的粗(第五次)

兩支測試檔的 `pytestmark` 只看 `INBOX_TEST_DB_URL`,
而 `tests/conftest.py::pg_models_engine` 用的是 `os.environ["INBOX_TEST_MODELS_DB_URL"]`。
只設第一個的話,測試會**開始跑**,然後 `KeyError`。

⚠ **症狀指向錯的地方**:`KeyError: 'INBOX_TEST_MODELS_DB_URL'` 看起來像「測試壞了」,
不像「你少設了一個環境變數」,於是人會去查 conftest 而不是去查自己的 env。
已改成帶訊息的 `skip`,訊息直接寫出補救指令。

**這是「斷言/守門的粒度比它宣稱保護的性質粗」的第五次**
(前四次:T09b 三處、T10b 的 `csrf_token` 空字串、T10c 的四段檢查、A-2 的 `grep -c` 假通過)。

#### 🔴 發現③:這條的副產品比它本身重要 —— B-4 不必再做

原訂 **指令稿 B-4** 是在 VM 上跑 `alembic downgrade base` → `upgrade head`,
補上「PG 15 雙向演練」那個 ⏳。而 CI 加了 `postgres:15.8-alpine`
(**刻意用與 VM 實測相同的 tag**)之後:

| | B-4(VM) | CI(T05b 之後) |
|---|---|---|
| 跑在 PG 15 | ✅ | ✅ 同一個 minor |
| 跑幾次 | **一次**,且要有人記得 | **每次 push,永久** |
| 對資料的風險 | 🔴 drop 掉**已部署庫**的 5 張表 | 🟢 一次性容器 |
| 多覆蓋到什麼 | 「這一個實例」的 downgrade | — |

`upgrade head` 已在 B-3 於那個實例上通過(連線字串與 scram 認證因此已驗),
所以 B-4 多覆蓋的只有「這一個實例的 downgrade」,而 downgrade 的 DDL 與實例無關。
→ **B-4 降為 🟡 可選**(第一條4:形狀改變先回寫文件),要不要還是跑一次由 Benny 決定。

### 捨棄的替代方案

| 方案 | 為什麼不用 |
|---|---|
| CI 裡 `apt install postgresql-15` | runner 的 apt 來源沒有 PG15;而且裝出來的版本會跟著 runner 映像漂,**漂了不會有人發現** |
| 用 `services: postgres:15`(不釘 minor) | 釘 `15.8-alpine` 才與 VM 實測的**同一個 minor**;「PG15 過了」與「**這個** PG15 過了」差一層 |
| 寫一個密碼進 `POSTGRES_PASSWORD` | 「這個字串算不算 secret」本身就是會吵起來的問題。用 `POSTGRES_HOST_AUTH_METHOD: trust` 就沒有這個問題 —— ⚠ 已在 `ci.yml` 註明**絕不可搬到任何部署用的 compose** |
| 用 `psql` 建第二個 database | psycopg 是 requirements 裡釘版的依賴;runner 上有沒有 `psql`、是哪個版本,不該影響測試跑不跑得動 |
| 用 grep 驗 `ci.yml` | 「有 `postgres` 這個字」會被**註釋**滿足。YAML 解析驗的是「有一個 image 是 postgres:15 的 service」 |

### 對現有資料的實際影響

## CI 實跑結果(`ci #46`,commit `4abf11c`,2026-08-29 補記)

**判準不是綠燈** —— 綠燈在 T05b 之前也是綠的(38 次)。逐項對驗收標準:

| 驗收標準 | 證據 |
|---|---|
| ② 輸出裡**沒有** `⚠ 其中 N skipped` | `188 passed, 1 warning in 21.17s` —— **零 skipped**,那一行沒有出現 |
| PG 版本是 **15** | postgres 的 log:`starting PostgreSQL **15.8** on x86_64-pc-linux-musl` |
| 兩個 env 真的傳進去了 | 步驟 env 印出兩行 `postgresql+psycopg://cats_inbox@localhost:5432/cats_inbox_{mig,models}` |
| 第二個 database 建起來了 | `✅ cats_inbox_models 已建立`(步驟 6 success) |
| 文件層 | `結果: 64 過 / 0 敗` |

🔴 **最硬的一項證據不在 pytest 的輸出裡,在 postgres 自己的 log 裡:**

```
ERROR: new row for relation "message" violates check constraint "ck_message_category"
ERROR: new row for relation "announcement" violates check constraint "ck_announcement_audience"
```

那是 `test_schema.py` 的**反向斷言**在 PG 15 上被真的拒收 ——
它證明的不只是「那 13 支沒有 skip」,而是**它們真的把 DDL 與 constraint 送到 PG 15 上執行了**。
⚠ 「沒有 skip」與「真的驗到了東西」是兩件事,而前者是我原本唯一打算檢查的。

→ **`docs/進度表.md` §6 第 2 項(PG 15 up→down→up)已結掉**,
且**從此每次 push 都跑**,不是一次性的演練。

### ⚠ 同一份 log 暴露我這一輪剛寫的程式碼有一個洞(第六次)

```
FATAL: role "root" does not exist        ← 每 10 秒一次,共 5 次
```

`--health-cmd pg_isready` **沒帶 `-U`**,於是它用容器裡的 OS 使用者(`root`)去試。
🔴 **健康檢查照樣回綠** —— `pg_isready` 只判斷「伺服器有沒有回應」,
而伺服器回一個 FATAL 也算有回應。也就是說:
**這個健康檢查在 `cats_inbox` 這個 role 根本沒建起來的情況下也會回綠。**

已改為 `--health-cmd "pg_isready -U cats_inbox -d cats_inbox_mig"`。

🔴 **而 `ci.yml` 的註釋必須把它改到什麼程度講清楚,不得含糊:**
帶了 `-U` 也**不會**讓它驗到 role 真的存在(`pg_isready` 不做完整連線)。
**真正擋住「role/database 沒建起來」的是下一步** ——
`create the second test database` 會以 `cats_inbox` 身分連進 `cats_inbox_mig`,
少了任一個就當場失敗。這次改的是**不要噴看起來像錯誤的 log**,不是改強度。
⚠ 把「噴的 log 少了」講成「檢查變嚴了」,就是製造下一個假信心。

**這是「斷言/守門的粒度比它宣稱保護的性質粗」的第六次,而這次在我自己剛寫的程式碼裡**
—— 上一段才剛把第五次寫進這篇日誌。
