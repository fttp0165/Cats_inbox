## 計畫段(動工前寫妥,第二條2)

### 目標

讓一個登入的人**看得到自己的訊息**,而且只看得到自己的:

1. `GET /inbox/api/v1/messages`(`?unread=true` 過濾)——列表,**收件人由後端判定**。
2. `GET /inbox/api/v1/messages/unread-count`——未讀鈴鐺(30 秒輪詢)。
3. `POST /inbox/api/v1/messages/{id}/read`——標已讀,**冪等**。
4. `GET /inbox/`——收件匣頁(伺服器端算繪、Bootstrap 5 **本地託管**、light、**階段一零人名**)。

T05 建的三個授權外殼(目前回 501)在本任務接上真實實作;
授權層本身一欄未動——那是 T05 的驗收,本任務不重做。

### 🔴 Bootstrap 從哪來:沿用平台既有的那一份,不下載

本環境**無法對外取得** Bootstrap(proxy 回 403)。但盤點發現
**平台已經有一份本地託管的 Bootstrap 5.3.8**:
`cats-portal/portal-admin/app/static/assets/vendor/bootstrap.min.css`(MIT)。

**決定:複製那一份過來**,連同它的 `LICENSE.txt`,並照 portal 的
`PROVENANCE.md` / `vendored.sha256` 慣例留下來源與雜湊。
理由:①版本與平台後台一致(視覺一致性是真的好處);②不必依賴外網;
③MIT 授權要求保留授權聲明,portal 已經在做,照抄它的做法最不容易漏。

🔴 **portal 那份 `PROVENANCE.md` 記了一個踩過的坑,本任務直接繼承它的教訓:**
> 放在 `static/vendor/` 的話,檔案在 repo 裡、路徑也算得對,
> **但 app 根本不會把它送出去** —— 瀏覽器拿到 404,整張清單畫不出來。
> 2026-08-03 第一版就是這樣上線的。

所以本任務要有一支**守門測試**:模板裡引用的每一個靜態資源,
都必須真的落在 `StaticFiles` 掛載的目錄底下。
⚠ 這個失敗模式的症狀是「整頁沒有樣式」,而**伺服器完全沒有錯誤**。

  `is_read` / `read_at` 兩欄,且**冪等**。

### 🔴 四項驗收各自對應一個「不會有錯誤訊息」的洩漏

| 驗收 | 壞掉時的症狀 | 測法 |
|---|---|---|
| 讀他人訊息 → **403** | 列表少一個 `WHERE` 就把全公司的通知端給任何人,而**畫面看起來完全正常**(就是訊息比較多) | 建一筆給別人的訊息,斷言①不出現在我的列表、②用它的 id 標已讀得到 403 |
| `sender_sub` 不信前端 | 任何人都能冒充任何人寄信,而收件人看不出差別 | 送一個帶 `sender_sub` 的 body,斷言它**被忽略** |
| UI 零外部 CDN | 沒有網路時整頁沒有樣式;或 CSP 上線後被擋 | 掃模板裡所有 `href`/`src`,斷言沒有 `http(s)://` 外部主機 |
| 階段一**零人名** | DI-3 未裁決前顯示姓名=**違反契約 §4.2a L1**(明文:不得出現在一般使用者可見頁面) | **先在快取寫一個姓名**,再斷言它**不出現在收件匣頁**上 |

🔴 最後那一條的測法是刻意的:斷言「頁面上沒有姓名」在快取是空的時候
**必然通過**——那是一支假綠的測試。先把姓名寫進去才是真的在測。
(與 T04 那支 `at_hash` 假綠測試同型;這次是動工前就想到,不是事後補。)

### 兩個要先定的設計問題

**① 別人的訊息 id → 403 還是 404?**
404 洩漏得更少(不確認資源存在),403 更好查。
**採 403**,理由:訊息 id 是 UUIDv4,**猜不到**——要打到這個端點,
你已經先有那個 id 了,所以 403 沒有多洩漏什麼。而 401/403/404 三者混用
會讓查問題的人分不出「沒登入 / 沒權限 / 不存在」。
⚠ 若日後 id 改成可猜的形式(序號),這個決定必須改回 404。寫進註釋。

**② 「冪等」的具體語意。**
第二次標已讀必須**不改變 `read_at`**——不是「不報錯」而已。
`read_at` 被第二次呼叫覆寫的話,「這則是什麼時候讀的」就永遠是最後一次
點擊的時間,而那個欄位存在的意義就沒了。測試斷言 `read_at` 不變。

### 驗收標準

   - `test_list_returns_only_own_messages`(別人的訊息不得出現)

2. 未登入打任何端點 → **401**;已登入無 `read_own` → **403**(不得混用)。
3. `bash tests/run_all.sh` 全綠且測試總數增加。
4. Bootstrap 的 `LICENSE.txt`、`PROVENANCE.md`、`vendored.sha256` 三件齊備
   (MIT 要求保留授權聲明;雜湊供日後比對是否被動過)。

### 與計畫段的偏離(第二條5)

**測試支數 11 → 14。** 多的三支都是寫的時候才發現「少了它就有一條沒被擋的路」:
`test_unauthenticated_read_is_401`(與 403 那條分開,證明兩者沒混用)、
`test_templates_reference_at_least_one_asset`(**掃到 0 個資源時下一支會空跑而通過**
——沿用 `run_all.sh` 對「探索到 0 支」的同一個原則)、
`test_vendored_files_match_recorded_hashes`。

🔴 **計畫段保持原文不改。**

### 為什麼這樣做(關鍵決策)

**① `repo.py` 的三個查詢函式,`recipient_sub` 都是必填且沒有「查全部」的分支。**
那個分支一旦存在,少寫一個參數的呼叫端就會把全公司的通知端出去,
而**畫面看起來完全正常**(只是訊息比較多,而沒有人覺得那是 bug)。
突變「列表少了 `WHERE`」轉紅。

**② 標已讀的查詢同時帶 `id` 與 `recipient_sub`,不是先查出來再比對。**
先查再比對會多一條「查到了但忘記比對」的路徑。

**③ 回應刻意不輸出 `sender_sub`。** 階段一它恆為 NULL,而把它放進回應
等於預告「階段二這裡會有一個人的 id」——到時候前端拿它去查姓名,
就繞過了 DI-3 的裁決。

**④ 收件匣頁未登入是 401,不是導向 IdP。** 契約對 upload-program 核准的
「未登入可見落地頁」偏離**只涵蓋首頁本身**,不涵蓋深層頁;深層頁未登入
該怎麼辦留給 T12 的入口整合決定。

### 測試結果(紅 → 綠的證據)

**紅:** `python3 -m pytest tests/test_inbox.py tests/test_static.py -q`
→ `11 failed, 3 passed`。⚠ 那 3 個 pass 有兩個是**空跑**
(`/inbox/` 當時 404,而 404 的內容裡自然沒有 CDN 字樣;資源清單當時是空的)
——這正是 `test_templates_reference_at_least_one_asset` 存在的理由,
它當時**紅**,明確指出旁邊那支在空跑。

**綠:** `bash tests/run_all.sh`(先 `eval "$(bash tests/pg_local.sh start)"`)
→ 文件層 **40 過 / 0 敗**、pytest **85 passed**,合計 **125 項全綠**(T07 結案時 111 項,+14)。

**突變檢查 9 項,全部被抓到**(明細見 `docs/TDD測試計畫表.md` §5.7)。

### 🔴 兩項發現

**1. 「零人名」那支測試原本有洞——只驗了 HTML,沒驗 API。**
突變檢查往 `_serialize` 加一個 `sender_name` 欄位,**測試照樣綠**:
模板沒有算繪它,所以頁面上看不到。**但前端 JS 拿得到**,
而契約 §4.2a L1 禁的是「出現在一般使用者可見的**面**」,JSON 欄位就是那個面。
已補兩條斷言:①API 回應不得出現快取的姓名字串;②**結構性**斷言
——回應項目不得有任何含 `name` 的鍵(擋「加了欄位但值剛好不是這次快取的
那個字串」,而那同樣是洩漏)。

⚠ 計畫段已經預先想到「先寫入姓名再斷言」這一層(避免快取為空時的假綠),
**但沒想到還有 API 那一面**。前者是動工前想到的,後者是突變檢查抓到的
——兩種機制抓到的是不同的東西。

**2. 量測工具第二次出問題:突變留在工作目錄裡,而 `git status` 看不出來。**
突變腳本的 write→test→restore 在同一秒內完成時,還原後檔案的
`(mtime, size)` 可能與 `__pycache__` 裡 `.pyc` 記錄的相符,
於是 Python **沿用由突變後原始碼編出的 bytecode**。
症狀:三支測試紅,而 `grep` 原始碼**完全正確** ——
查的人會先懷疑程式,而問題在 bytecode。
定位方式是列舉 route 的相依,看到 `GET /messages` 掛的是 `current_identity`
而不是 `require_capability._guard`,才確定是 stale `.pyc`。
已在腳本每次還原後清 `__pycache__`。
🔴 這是**不把突變腳本放進 repo**(T04 的決定)的第二個具體理由:
它改寫工作目錄,而**還原不是原子的**。

### 對現有資料的實際影響

`is_read` / `read_at` 兩欄且冪等。
未動 portal、未動 VM、未動已建立的 client。

### 遺留問題與後續建議

1. **列表沒有分頁**,只有 `limit=50`。上線後訊息累積起來,第 51 則就看不到了
   ——⚠ 這不是「效能問題」,是**功能缺口**,而它在測試資料只有兩三筆時
   完全看不出來。建議 T12 上線冒煙前補 cursor 分頁(`created_at` + `id`)。
2. **未讀鈴鐺的前端還沒接**(portal-landing 側,T12)。本任務只交付端點。
3. ⚠ **`GET /inbox/` 未登入回 401 而非導向**——T12 要決定深層頁的行為。
   契約對 upload-program 的核准偏離只涵蓋首頁本身。
4. **Bootstrap 升版要從 portal 同步**,不要各自從網路抓(兩邊會漂到不同的
   patch 版,而 CSS 的差異在畫面上是「某個元件的間距不太一樣」,沒有人會查)。
   已寫進 `PROVENANCE.md`。
5. T10 會加嚴格 CSP + nonce,屆時 `inbox.html` 的 `<style>` 要補 nonce
   (已寫在模板註釋裡)。漏掉的症狀是整頁沒有樣式,不是錯誤訊息。
