## 🔴 A 段第一次執行:三項回寫,其中一項是我造成的資安事件(2026-08-28 22:40)

### ① 🔴 我的指令把 client secret 印到畫面上,而它進了對話紀錄

稿的 A-2 寫「`INBOX_OIDC_CLIENT_SECRET` 從 **VM 上的** 交付檔取」,
而我在對話裡給的取法是:

```
sudo grep -n 'CLIENT_SECRET\|INTERNAL_BASE' /opt/cats-portal/idp/.env.keycloak.cats-inbox
```

**`grep` 會把值印出來。** Benny 照著做,輸出貼回對話 ——

🔴 **這違反的是一條寫在那個檔案自己裡面的規則。** portal 的
`idp/bootstrap/client-cats-inbox.sh` 產生交付檔時就寫進去了:

> 🔐 本檔含 client secret:不進 git(.gitignore 已擋)、**不貼聊天/工單**。

而該腳本第 46 行的註釋是「🔴 secret 一律不印在畫面上(**2026-07-27 教訓**)」。

**規則在文件裡,而違反它的是同一份文件給的操作步驟。**

**處置:**

### ② 🔴 要填的是四處,不是三個 —— `INBOX_DB_URL` 沒有密碼

`app/config.py:76` 把 `INBOX_DB_URL` **逐字**當連線字串用,而 `.env.example` 原本是
`postgresql://cats_inbox@cats-inbox-pg:5432/cats_inbox` —— **沒有密碼**;
同時 compose 給 pg 設 `POSTGRES_PASSWORD`,postgres 官方映像在有密碼時以
scram-sha-256 要求驗證。

🔴 **為什麼所有測試都沒抓到**:測試走 `INBOX_TEST_PG_URL`(本機 PG,自己帶認證),
**從不讀 `.env.example` 的那一行** —— 那一行只在真的部署時才被使用。
⚠ **症狀還會指錯方向**:健康檢查刻意不查 DB(T01 的設計),所以容器 healthy、
`/inbox/health` 回 200,而 **B-3 的 `alembic upgrade head` 才失敗** ——
看起來像 migration 壞了,實際上是連線字串少了密碼。

**這是同一個形狀的第三次**(T10c 的映像、T10d 的 alembic、本次的連線字串):
**每份文件都對,而把它們接起來的那一步不在任何人的清單上。**

處置:紅測試 `test_env_example_db_url_carries_a_password_slot` **先紅後綠**;
`.env.example` 改為 `__SAME_AS_POSTGRES_PASSWORD__` 佔位字串;
稿的腳本一次寫入四處。
🔴 並改用 `hex` 而非 `base64` 產生密碼 —— `base64` 會產生 `/`,
而它要出現在 `user:密碼@` 位置,`/` 在那裡會被當成路徑分隔。

### ③ ⚠ `grep -c` 的期望值我數錯了(13 → 14)

`.env.example` 有 **14** 個 `INBOX_`/`POSTGRES_` 變數;`COMPOSE_FILE` 不符那個 pattern。
