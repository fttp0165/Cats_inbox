### 🔴 寫的過程中改變了 T11b 的形狀:只有最後一段需要低峰窗口

原本 T11b 被當成一個「2–3 小時的低峰窗口任務」。逐步寫下來之後發現
**四段裡只有一段真的會動到正式站**:

| 段 | 內容 | 需要低峰窗口? |
|---|---|---|
| **A** | VM 建 `/opt/cats-inbox`、`.env`、併 secret、拉映像 | ❌ 不需要 —— 對正式站零影響 |
| **B** | 容器起來、跑 migration、驗上游可解析 | ❌ **不需要** —— gateway 上還沒有 `/inbox/` 路由,**沒有任何流量會進來** |
| **C** | portal repo 改動(解註解 + 白名單 + staging)+ 跑 staging `verify.sh` | ❌ 不需要 —— 改 repo 與跑 staging 都不碰正式 gateway |
| **D** | `ops/gateway-apply.sh` 套用 + 冒煙 | ✅ **只有這一段** |

🔴 **這件事本身就是交付物的一部分**:窗口從「2–3 小時」縮到**約 10 分鐘**,
而前面三段可以在任何時間慢慢做、做錯了也不影響任何人。
⚠ 前提是**順序不可顛倒**(B 必須在 C 的白名單之前,因為白名單的入場券是 B 的實測)。

### 🔴 一個容易寫錯的地方:C 段不在 VM 上做

解註解、改白名單、加 staging 假上游**都是 portal repo 的改動** ——
路由權威在 portal repo,而**在 VM 上直接改 `/opt/cats-portal` 的檔案等於繞過 PR**。
⚠ portal 憲法 v1.9 記載的第二次事故正是這一類:VM 在另一條分支上,
`git pull` 回「Already up to date」而設定根本沒變,**`nginx -t` 過、reload 成功,套用完全落空**。
→ C 段標明**在開發者本機 + 分支**;D 段的 VM 才 `git pull`,而且**要驗 commit 對得上**。

上面第 2 項寫「這份稿沒有被執行過」。Benny 當天就貼了第 0 步,而它**失敗了**:

```
fatal: not a git repository (or any of the parent directories): .git
fatal: not a git repository (or any of the parent directories): .git
fatal: not a git repository (or any of the parent directories): .git
```

### 這與 portal 2026-08-03 事故① 字面上相同,而**原因不同**

| | portal 2026-08-03 ① | **本次** |
|---|---|---|
| 症狀 | 三行全部 `fatal: not a git repository` | **一模一樣** |
| 原因 | 指令只寫「在你本機或 UI」,被**貼到 VM 的部署目錄** | 🔴 **貼在對的目錄**(`~/Cats_inbox`),而**我假設了它是 git clone** |
| 第九條11 有沒有擋住 | ❌ 沒有(當時還沒有這條) | ⚠ **標了,但它管不到這件事** |

🔴 **這是第九條11 的一個真實邊界**:它要求標「工作目錄」,而**沒有涵蓋
「那個目錄是什麼」**。標示是對的、貼的人也貼對了,而假設是錯的。
⚠ 提醒:這不是要在條文裡再加一款(第九條自己警告過插隊與膨脹);
**做法是在指令裡放前置檢查**,讓錯的假設當場說出自己錯在哪。

### 處置(指令稿 **v1.1**)

1. 🔴 **第 0 步改為 GitHub UI 優先。** 它不需要本機 clone,而且
   **Release 頁一次建立 tag 與 title+content** —— 「先推裸 tag、之後再補 Release」
   中間那段時間本來就**違反第八條1**。**UI 這條路一開始就更對,我把它排在第二。**
2. 本機那條路保留為備用,最前面加 `git rev-parse --git-dir` 前置檢查 ——
   少了它,三行指令變成三個 fatal 而**看不出為什麼**。
3. UI 步驟特別標出 **Target 那一格**(決定 tag 指向哪個 commit,預設值不一定是那條分支)。

### 給本機那個目錄的診斷(不刪任何東西)

⚠ `~/Cats_inbox` 裡若有**只存在於那台機器**的編輯(因為它不是 repo,
所以沒有任何地方有副本),**不要刪它**。先看它是什麼:

```bash
ls -a ~/Cats_inbox | head
find ~ -maxdepth 3 -name .git -type d 2>/dev/null
```

- 有 clone 在別的路徑 → `cd` 過去用那個;
- 到處都沒有 → `git clone https://github.com/fttp0165/Cats_inbox.git ~/Cats_inbox-git`
  (**clone 到新目錄**,不覆蓋原本那個)。

## 🔴 第二次執行的結果:第 0 步完成了一半(2026-08-27 17:00,第二條5 回寫)

Benny clone 之後走**備用路徑**推 tag,結果:

| 事 | 結果 |
|---|---|
| `git push origin v0.1.1` | ✅ 成功(`Enumerating objects: 1` = 只推 tag 物件,commit 已在 origin) |
| tag 指向 | `0dbed77`(含全部內容;三道一致性檢查因此全過) |
| `release-image #2` | ✅ **success**,60 秒、8 步全過 |
| GHCR | ✅ `tags/list` 回 `["0.1.0","0.1.1"]` —— **無 `latest`**(離開 GitHub 問 registry 驗的) |
| **Release 頁** | 🔴 **不存在**(API 查 `v0.1.1` 回 **404**)|

### 🔴 根因:提醒不是步驟

v1.1 把「推完 tag 要立刻去 Release 頁補 title 與 content」寫成**一行 `⚠` 提醒**,
放在編號指令區塊的**後面**。而**照著清單做的人會做完編號的最後一項就停** ——
於是 tag 推出去了、CI 綠了、映像上了 registry,而**裸 tag 的狀態持續著**,
第八條1 沒有被滿足。

⚠ **這與 v1.1 那次是同一個形狀的錯,只是換一層**:
v1.1 的錯是「我假設了那個目錄是 repo」;這次是「我假設了讀的人會把 `⚠` 當成待辦」。
**兩次都是把某個必要條件寫在編號步驟之外。**
