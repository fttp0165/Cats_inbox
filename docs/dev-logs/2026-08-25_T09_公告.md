## 計畫段(動工前寫妥,第二條2)

### 目標

把 M3 的「公告先行」做成**使用者真的看得到**的東西:

1. `POST /inbox/api/v1/announcements` — 發布(需 `announcer` 能力),取代 T05 留下的 501 外殼;
2. `GET /inbox/api/v1/announcements/active` — 有效公告 + **這個人**讀過沒;
3. `POST /inbox/api/v1/announcements/{id}/read` — 逐人已讀(冪等,不複製列);
4. 收件匣頁 `GET /inbox/` **顯示有效公告**。

### 🔴 第 4 項是本任務對計畫的擴充,先講清楚為什麼(第一條4)

任務表 T09 那一列只寫了三個 API,**沒有任何一條寫「把公告畫出來給人看」**。
而下一個里程碑 M4 的名字是「**公告中心上線**」,其下的 T11 是 gateway 路由、
T12 是冒煙 + 入口鈴鐺 —— 兩者都不含公告的畫面。

🔴 **也就是說:照現在的任務表走完 M4,公告上線之後沒有任何一個畫面顯示它。**
沒有人會收到錯誤訊息,發布 API 會回 200,`active` 也會回得出來。
這與我在 D01 記下的形狀相同:**守門存在、看起來在運作,而它只覆蓋了一部分對象。**

處置(依第一條4「需求變更先更新任務表再依新任務執行」):
- 本任務把**讀的那一面**(收件匣頁顯示公告)納入 T09,並回寫任務表 T09 那一列;
- **寫的那一面**(給 `announcer` 用的發布表單)另立 **T09b**,不混進本任務——
  它需要表單、CSRF、輸入驗證的 UI,估時與本任務相當;
- T12 那一列補一條驗收:**入口鈴鐺要不要把公告算進未讀,必須明講**
  (現在 `messages/unread-count` 只數訊息;不明講的話公告在入口頁零信號)。

### 驗收標準

任務表原有三條 + 本任務自加四條。**每一條都對應一種不會有錯誤訊息的失敗:**

| # | 驗收 | 壞掉時的症狀(為什麼要有這一條) |
|---|---|---|
| 1 | 非 `announcer` 發布 → **403 且零列寫入** | 只驗狀態碼的話,「先寫入再回 403」照樣綠 |
| 2 | 過期公告不出現在 `active` | — |
| 3 | 已讀**逐人一列**,重複標不複製列、`read_at` 不被覆寫 | 覆寫的話「這則是什麼時候讀的」永遠是最後一次點擊,而兩次都回 200 |
| 4 | **未來的**公告不出現在 `active` | 只驗 `ends_at` 是最容易漏的一半:排程下週的公告**當場就出現**,而發布者以為排程有效 |
| 5 | 甲讀過**不會**讓乙的那則變成已讀 | 公告若把已讀寫在公告本身,一個人讀完全公司都變已讀,**其他人只是覺得自己好像看過** |
| 6 | `ends_at <= starts_at` → **400 拒收** | 空窗公告=發布成功但永遠不出現,回 200 而沒有任何錯誤 |
| 7 | **不帶時區**的時間 → **400 拒收** | 台灣同事輸入 `02:00` 存成 UTC 就差 8 小時,公告晚 8 小時出現而零錯誤(portal 憲法第四條7 記載的同一種坑) |

另:`active` 的回應**不得含 `author_sub`、不得含任何姓名**(契約 §4.2a L1、DI-3 未裁決)
——與 T08 `_serialize` 同一條紅線,需有測試。

### 為什麼這樣做(關鍵決策)

**① 不帶時區的時間一律 400,不預設當成 UTC,也不預設當成 UTC+8。**
台灣同事輸入 `2026-08-30T02:00:00` 想的是 UTC+8;當 UTC 存進去差 8 小時,
公告**晚 8 小時才出現而沒有任何錯誤訊息**。預設成 UTC+8 也不行——那讓 API
只對台灣正確,而錯的那次一樣沒有錯誤。**要求呼叫方明講是唯一不會猜錯的做法。**

**② 公告不存在回 404,而訊息的同一種情況回 403。**
差別在**有沒有歸屬要保護**:訊息有(「這是不是你的」),回 404 會洩漏
「這個 id 存在」;公告對所有人可見,沒有歸屬,此時 403 會讓人以為是自己
權限不足,查錯方向。兩個決定都寫在各自端點的註釋裡,不是憑感覺選的。

**③ `active` 的未讀數由同一次查詢算出,不另發 count 查詢。**
兩個查詢跑在兩個時間點,而「顯示 1 未讀但清單裡每則都已讀」的畫面
**看起來像資料庫壞掉**。訊息那邊的 `unread-count` 是獨立端點(鈴鐺專用,
成本要低),這裡不是,所以做法不同——不同是刻意的。

**④ 公告排在訊息之前(頁面與圖都是)。**
公告一則對多人且通常有時效(維護時段、政策變更),排在下面等於沒發。

### 🔴 兩項發現

**① `user_sub` 放錯位置的症狀不是「已讀錯了」,是公告會消失。**
把它從 LEFT JOIN 的 `ON` 搬到 `WHERE`,對「別人讀過而我沒讀」的公告,
join 配出的是**別人的**已讀列,然後被 WHERE 濾掉 ——
**別人一讀,那則公告就從我的清單裡不見了**。而不見的東西沒有人會回報。
理由已寫進 `app/repo.py` 該查詢的註釋,不只寫在這裡。

**② D01 的商業邏輯圖把「公告發布 API」畫成實線(=已實作),而當時它是回 501 的授權外殼。**
那正是 D01 自己列為決策①要避免的事:「架構圖最常見的謊是把設計畫成現況」。
T09 讓那句話變成真的 —— 但 **那不是圖對了,是現實追上了圖**。
⚠ 已在架構說明 v1.1 的版本歷史裡如實記為自我更正,不靜默帶過。

### 遺留問題與後續建議

1. 🔴 **公告發布沒有畫面** → 已立 **T09b**(2–3 h)。目前 `announcer` 只能用 curl。
2. 🔴 **入口鈴鐺不數公告** → 已寫進 **T12** 的驗收。`messages/unread-count` 的名字
   就叫 `messages`,本任務刻意沒改它的語意;不處理的話**公告在入口頁零信號**,
   而每一層都回 200。
3. ⚠ **`active` 沒有上限也沒有分頁**。有效公告通常只有個位數,但那是**慣例不是約束**
   ——與收件匣的 `limit=50` 是同一類缺口,一併列在架構說明 §5.2。
4. 💡 `announcement_read` 只增不減。公告刪除時由 CASCADE 帶走;**公告不會被刪**時
   這張表隨人數線性成長。目前不處理(規模不到),但值得在 M4 回報實測時一起看。
