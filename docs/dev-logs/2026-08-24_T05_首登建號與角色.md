## 計畫段(動工前寫妥,第二條2)

### 🔴 先處理一個排程相依,不是先寫程式(第一條4)

T05 的驗收標準有四條是**資料庫斷言**:「user 表只存 `sub`+角色」「首登 DB 只多一列
(無 email/密碼欄)」「`reader` 可單獨停用」「快取清除工具實測」。
而建表與 migration 排在 **T07**。

**決定:把 `app_user` 與 Alembic 基礎設施從 T07 提前到 T05。** 理由:

1. 記憶體版角色**無法驗證上述四條**中的任何一條——「DB 只多一列」在沒有 DB 時
   不是「先過再說」,是**這句話沒有意義**。
2. `display_name` 的 L1 快取紅線要求「附**整批清除**工具」。記憶體快取重啟就沒了,
   清除工具會變成一個永遠成功的空操作——**那比沒有工具更糟,它讓人以為有**。
3. portal 核可條件 C2 要求 `reader` 可由本專案後台**單獨停用**,C4 給 portal
   **單方撤回權**。兩者都需要一個「關掉之後重啟仍然是關的」的狀態。

**T07 因此縮為三張表**(`message` / `announcement` / `announcement_read`)。
🔴 **同一次提交回寫 `docs/任務表.md` 與 `docs/TDD測試計畫表.md`**(第一條4:
需求變更不直接改程式,先更新任務表)。

### 目標

讓一個真人登入後**有身分、有角色、而且只拿到該拿的**:

1. **首登建號**:`app_user` 只存 `sub`;**無 email、無姓名(除 L1 快取欄)、無密碼欄**。
2. **自動授 `reader`**(DEC-16 經核可的偏離),可及動作**僅限自我範圍讀取**。
3. **deny-by-default**:`sender` / `announcer` / `admin` 一律不自動給;無角色打業務 API → **403**
   並導向待開通頁(顯示本人 `sub`,契約 §4.3 的雞生蛋解法)。
4. **bootstrap 管理員清單每次登入比對**:冪等、**已停用者不得復活**。
5. **角色後台** + **`display_name` L1 快取**(僅本人 token 寫入、僅管理後台顯示、
   附整批 + 單筆清除工具)。

### 🔴 四條核可條件如何各自落到可執行的東西上

portal 2026-08-18 的核可附四條件,它們**同列本專案紅線**。逐條寫出落點,
否則「已符合」只是宣稱:

| 條件 | 落點 | 怎麼證明 |
|---|---|---|
| **C1** 範圍寫死在自我範圍讀取 | `app/authz.py` 的 `ROLE_CAPABILITIES` 常數;`reader` 只映射到自我範圍讀取 | 反向測試:`reader` 打寄信/發公告 → 403 |
| **C2** `reader` 須可由本專案後台**單獨停用** | `user_role.enabled` 欄(per-user)+ `INBOX_AUTO_GRANT_READER`(全域) | 停用後同一人再登入不得復活其 reader |
| **C3** 以**反向測試**釘住 C1 並納入 CI | `tests/test_authz.py` 兩支反向測試 | 先紅後綠,進 `run_all.sh` |
| **C4** portal 得**單方撤回** | 全域開關關掉後回到**全 deny** | 測試:關閉後首登得到零角色 → 403 + 待開通頁 |

⚠ **C2 的兩層是刻意的,且代價要講清楚**:per-user 停用即時生效;
全域開關是 env,**需重啟才生效**。撤回是罕見且刻意的動作,可接受;
但這是**已知限制**,不是沒想到。若 portal 要求「即時撤回」,那需要一張設定表(另案)。

### 為什麼這樣做(關鍵決策)

**① `app_user` + Alembic 從 T07 提前。** 理由寫在計畫段,結果證實了它:
`test_display_name_purge_tool_clears_bulk_and_single` 與
`test_reader_can_be_disabled_per_user` 兩支都**需要跨重啟仍然存在的狀態**,
記憶體版寫不出來。

**② 把 T04 的續期邏輯從 closure 抽到 `app/deps.py`。**
T04 時它只服務 `/me`,而 T05 一加業務端點就發現:契約 §3.3 的續期必須發生在
**每一個**已認證請求上。留在 closure 裡的話,T08 起每個端點都要自己接一次,
而**少接的那一個就是「登入 5 分鐘後這個頁面莫名變未登入」,伺服器零錯誤**。
抽成一處之後,忘記接的症狀是 401(明顯),不是靜默失效。

**③ 角色每次請求都查 DB,不快取在 session 裡。**
管理員停用一個角色之後,那個人手上的 session 還活著。快取進 session 等於
「停用要等他重新登入才生效」——而他不會重新登入。這會把 §3.3 用 300 秒
access token 換來的收權即時性在這一步抵銷掉。

**④ 業務端點已授權時回 501,不回 200 空清單。**
200 空清單會說「你沒有訊息」——那是**假話**,因為表還不存在。
501 說的是「你有權限,但這個功能還沒做」,那是真的。

**⑤ `user_role` 用 `enabled` 而不是刪列。**
刪掉之後 bootstrap 清單比對會把它當成「還沒給過」而重新授與
——停用因此在清單成員身上**永遠無效**,而畫面上完全正常。
`grant_role()` 也刻意**不**復活已停用的角色(同一個理由)。

**⑥ `admin` 刻意不含 `read_own`。** 管身分與讀信是兩件事;綁在一起會讓
「單獨停用 reader」(C2)對管理員失效。管理員要讀自己的信時,他身上另外有
首登就給的 `reader`。

### 🔴 三項發現

**1. 替身少了 `name` claim ——`at_hash` 那個坑的第二次。**
`test_display_name_purge_tool...` 一開始紅在「前置:登入時應已寫入 L1 快取」,
看起來像程式沒寫;實際是**替身沒給 `name`**。真實 Keycloak 在 `profile` scope
在位時會給 `name`/`given_name`/`family_name`(portal 建 client 時刻意保留
`profile`、只移除 `email`)。這與契約 v3.2 記載的 PLM `at_hash` 事故**完全同型**
——替身比真實 IdP 寬鬆。已補進替身並在該處寫明理由。

**2. 相對路徑讓同一支測試在兩個入口點結果不同。**
兩支 AST 檢查原本寫 `pathlib.Path("app/authz.py")`,而 `run_all.sh` 是
`cd tests/` 之後才跑 pytest ——**從 repo 根跑 61 綠、經 `run_all.sh` 跑 2 紅**,
而紅的訊息看起來像程式壞了。已一律改用 conftest 的 `ROOT`。

**3. `test_downgrade_is_not_a_stub` 自己寫錯。**
它把**所有** `ast.Expr` 都當 docstring 濾掉,而 `op.drop_table(...)` 本身就是
一個 expression statement —— 於是每一個**正確的** downgrade 都會被判成空的。
⚠ 它第一次跑就紅,而**紅的原因在測試自己身上**;真正的 up→down→up 演練
同時獨立通過,兩個角度裡不夠力的那個剛好是它。

### 遺留問題與後續建議

1. 🔴 **PG15 演練未做**(本機只有 PG16.13、無 docker daemon)。
   `tests/test_migration.py` 的檔頭與任務表都已誠實標註。
   **列入 T11**:在 VM 上以真正的 PG15 跑一次 up→down→up。
2. ⚠ **應用層測試用 SQLite,schema 來自 `create_all()` 而非 migration。**
   兩者若漂移,應用層測試不會發現。`test_schema_has_no_identity_columns` 補了
   一半(驗 migration 產出的 schema),但**沒有一支測試在比較兩者**——
   建議 T07 加一支 `create_all()` vs migration 的 schema 差異比對。
3. **`/inbox/me` 目前是 callback 的導向目標**,而它現在會回 `roles`。
   T08 收件匣首頁上線後改導向首頁;屆時零角色的人應導到 `/inbox/pending`。
4. ⚠ **T05 沒有做「admin 派角色給別人」的端到端測試**——後台的 POST 路由有
   寫,但測試只驗了「reader 進不去、admin 進得去」。派角色的實際效果
   由 `repo` 層的測試覆蓋。建議 T08 補一支經 HTTP 的完整往返。
5. 💡 `tools/purge_display_names.py` 刻意做成 CLI 而非只有後台按鈕:
   「整批清除」最需要被執行的時刻之一,正是「這份快取不該再存在」——
   那時候可能沒有人有 admin 角色。
