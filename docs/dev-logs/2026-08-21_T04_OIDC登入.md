## 計畫段(動工前寫妥,第二條2)

### 目標

讓一個真人可以從 `https://catsapp.sporton.com.tw/inbox/` 走 Keycloak 登入回來,並且**在 5 分鐘後仍是登入狀態**。

具體交付四件事:

1. **Authorization Code + PKCE(S256)** 的 `/inbox/oidc/login` 與 `/inbox/oidc/callback/`,含一次性 `state` 與 `nonce`。
2. **id_token 驗證**:RS256 only、JWKS(快取 1h、依 `kid` 選鑰、支援輪替)、驗 `iss`/`aud`/`exp`,時鐘容忍 **±30s**。
3. **伺服器端主動 refresh**(契約 §3.3 陷阱)——access token 只有 300 秒,而伺服器端算繪的 App **不會有人幫它 refresh**。
4. **session cookie**:`Path=/inbox/`、`HttpOnly`、`SameSite=Lax`、`Secure`(契約 §4.10 同源義務;token 一律不進 localStorage、不進前端)。

🔴 **為什麼 T04 是整個 M2 最容易「測試全綠但真人登不進去」的一步。** 契約列了三個坑,三個都已經有人踩過,而**三個都不會有錯誤訊息**:

| 坑 | 症狀 | 誰踩過 |
|---|---|---|
| `redirect_uri` 與登記值不逐字相同 | 錯誤停在 **Keycloak 的頁面**,自家 app 的 log 是**空的** | PLM(契約 v2.14) |
| 不做 refresh | 登入 5 分鐘後**靜默**退回未登入,伺服器**零錯誤** | upload-program(契約 §3.3) |
| 測試自造的 token 少一個真實 IdP 會給的 claim | **400 多支離線測試一支都沒抓到**,開旗標當天第一個真人登入 100% 失敗於 `at_hash` | PLM(契約 v3.2) |

本任務的測試設計就是照這三個坑反推的,不是照「函式有沒有回傳正確值」寫的。

   `test_fake_idp_token_carries_real_claims` / `test_redirect_uri_matches_registered_value` / `test_login_route_issues_pkce_s256`。

3. 🔴 **`at_hash` 的行為必須明確**:PLM 的事故不是「沒驗 at_hash」,是**函式庫因為多了那個 claim 而改變行為**。本專案必須二者擇一並**以測試斷言**:要嘛驗(需傳 access_token),要嘛明確關閉。選定後寫進註釋說明為什麼。

5. **±30s 是雙向的**:過期 29 秒要**通過**,過期 31 秒要 **401**。只測一邊等於沒測 leeway。
6. **401 與 403 不得混用**(契約 §11.5 的分界對 T04 同樣適用):token 無效=401,已認證但無權=403。
7. `bash tests/run_all.sh` 全綠,且**測試總數增加**(新測試真的被收集到)。

⏳ **本任務做不到、必須等 T11 的三項**(誠實標註,不假裝):
① 真人端到端登入;② 用壞 code 打 token 端點驗 secret(契約 v2.17,回 `400 invalid_grant` 即 secret 正確);③ 容器內 discovery 走 `OIDC_INTERNAL_BASE` 而 `iss` 維持對外的實際連通。**三項全部寫進遺留問題,不寫進驗收。**

純新增檔案 + 三處小修改,**無 migration、無資料異動**。

1. `git revert <T04 commit>` 即回到 T03b 結案狀態。

另外多了兩個計畫沒列的檔案:`app/clock.py`(時鐘要能注入,見決策②)與

### 為什麼這樣做(關鍵決策與捨棄的替代方案)

**① session 放伺服器端,不放簽章 cookie。**
捨棄的方案是把 token 塞進簽章 cookie(無狀態、免儲存)。**它做不到 T06。**
契約 §10.3 的 front-channel logout 是 **IdP 主動呼叫**我方端點、帶一個 `sid`
——那一刻**使用者的瀏覽器不在現場**。無狀態 cookie 只有瀏覽器有,
於是「IdP 通知得到,我方卻無從作廢」,症狀是**入口登出了而 inbox 還登入著**
(契約 §10.7 的實例)。代價誠實記在 `app/session.py` 檔頭:
**重啟即全員重新登入**(刻意不裝 Redis)、**單一容器有效**。

**② 時鐘做成參數,不用 `time.time()`。**
PyJWT 的 `jwt.decode` 內部用 `time.time()`,**沒有注入時鐘的地方**,
所以 `exp`/`iat` 改成自己驗(`options={"verify_exp": False}`)。
換來的是 ±30s 與 300 秒續期兩條都能自動測——否則只剩「`sleep(301)`」
(沒人會跑)或「大概對」(等於沒斷言)兩種選擇。

**③ `redirect_uri` 用字串組合,不用任何反查路由的機制。**
這是契約 v2.14 的直接落點:PLM 用 Django `reverse()` 動態組,而 `reverse()`
回**後註冊**的掛載點,實際送出值與登記值不同 → 首登即 mismatch,
**錯誤停在 Keycloak 頁面、自家 log 是空的**。我方連 Host header 都不採信
(代理可改寫),改用明確的 `INBOX_PUBLIC_BASE_URL`,並印 log 供逐字比對。

**④ `at_hash` 的行為明確選定並斷言**(驗收第 3 項):
claim 存在 + 有 access_token → **必須相符**;claim 存在但無 access_token →
**跳過不拋錯**(PLM 當天炸的就是這條);claim 不存在 → 跳過(符合規範)。

**⑤ 登入不做授權判定。** 首登建號、自動授 `reader`、待開通頁一律留 T05。
理由:混在一起之後,portal 核可條件 C2「`reader` 須可單獨停用」就沒有下手的地方。

### 🔴 三項發現

**1. `.env.example` 與 portal 交付檔的 `INTERNAL_BASE` 形狀不一致。**
我方原寫 `http://keycloak:8080/auth/realms/sporton`,而 portal 的
`idp/bootstrap/client-cats-inbox.sh` 交付的是 `http://keycloak:8080/auth`
(**不含 realm**;realm 由程式自 `ISSUER` 推導後接上)。
照舊值部署會組出 `/realms/sporton/realms/sporton` → discovery **404**。
**離線測試全綠,而它只在第一個真人登入時出現**——與 PLM 的 `at_hash` 同型。
已修,並加 `test_env_example_oidc_values_match_portal_delivery_shape` 釘住形狀。

**2. 突變檢查抓到一支「假綠」的測試。**
`test_rejects_hs256_and_none_alg` 原本綠的理由不是它宣稱的那個:替身簽的
HS256 假 token **沒有 `kid`**,所以拆掉 alg 閘門後,token 是在「找不到 kid」
那一關被擋的。已修——簽錯演算法的假 token 一律帶真實存在的 `kid`
(演算法混淆攻擊的標準做法就是從真 token 抄走 kid,只換 alg)。

**3. 三層防護全拆時會漏出 `TypeError` 變成 500。**
拆到最後一層才看見:PyJWT 拒絕用非對稱金鑰做 HMAC,丟的是 `TypeError`
而不是 `InvalidTokenError`,於是逃出既有的 except 變成 **500**。
已加一道「任何未預期解析錯誤一律 401」。500 的代價有兩層:
告訴攻擊者他找到了未處理路徑,也會在半夜把人叫起來。
