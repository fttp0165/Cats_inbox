## 計畫段(動工前寫妥,第二條2)

### 目標

建三張表 + 一條 migration(`0002`),讓 T08–T10 有東西可以讀寫:

| 表 | 用途 | 來源 |
|---|---|---|
| `message` | 系統通知(階段一)+ 人對人站內信(階段二) | 上游《站內信通知中心設計規劃》**§4.1** |
| `announcement` | 公告 | 上游 **§4.2** |
| `announcement_read` | 公告的逐人已讀 | 上游 **§4.2** |

🔴 **欄位名一律照上游 §4 逐字沿用**(含 `announcement.title` 與 `message.subject`
用詞不一致這件事)。理由不是懶:上游 §2.1 的「退路保留」明文寫著
「併回 compliance 的成本=**搬四張表** + 改 upstream」。
改欄位名會讓那句話**當場失效**——搬表就變成一次資料遷移。
用詞不一致是可見的papercut;改名是不可見的成本。

### 影響範圍

🟡 **第二條 migration**(`0002`,接在 T05 的 `0001` 之後)。

- **對現有資料的影響:🟢 不動任何既有資料**——本服務尚未上線,只有 CREATE TABLE。
  `0001` 建的 `app_user` / `user_role` **一欄未動**。
- 新增:`app/models.py` 三個 model、`alembic/versions/0002_*.py`、`tests/test_schema.py`。
- **不寫任何 API**——讀寫端點是 T08/T09,本任務只有 schema。

### 🔴 三個刻意的設計決定(它們都會被誤讀成疏漏)

**① `message.recipient_sub` **不設** 外鍵到 `app_user.sub`。**
推送 API(T14)必須能推給**從未登入過 inbox 的人**——新到職的同事、
或 PLM 那 50 位沒有 email 的測試工程師。設了外鍵,那些推送會被資料庫擋掉,
而症狀是「通知沒送到」,**收件人自己不會知道有東西被丟掉**。
故 `recipient_sub` 只建索引、不設外鍵,並以測試**斷言外鍵不存在**
(否則日後有人「順手補上」會靜默地把這個能力關掉)。

**② `announcement_read.user_sub` **要**設外鍵(CASCADE)。**
與 ① 相反是刻意的:要標記公告已讀,你**必然已經登入過**,所以那一列必定存在。
而公告被刪除時,它的已讀紀錄應該跟著走。
⚠ 兩張表對「sub 要不要設外鍵」給出相反的答案 —— 這在日後看起來會像不一致,
所以理由寫進 migration 與 model 的註釋裡,不只寫在這篇日誌。

**③ `category` / `audience` 用 `String` + CHECK,不用 PostgreSQL 的 enum 型別。**
PG 的 enum 要加一個值得下 `ALTER TYPE`,而那在 migration 裡是一段
不能回滾的操作(舊版 PG 無法從 enum 移除值)。用 CHECK 約束的話,
加一個 category 就只是改約束,`downgrade` 也寫得出來。

### 🔴 一項要主動揭露的發現(動工前就看得到)

上游 §4.2 的 `announcement.audience` 寫「`all` / **群組**」。
**群組定向我方現在做不到,而且不是工程問題:**
它需要 `groups` claim,而我方的 client **刻意沒有申請 groups**
(T03 申請書〈貳〉明載「不申請 `email`、不申請 `groups`」)。

處理方式:欄位照上游建、**預設 `all`**,並在 model 與 migration 註釋標明
「群組定向需另向 portal 申請 §4.2a L2,未申請前只接受 `all`」。
T09 的公告發布會以 CHECK 把它擋在 `all`。
**不建欄位是錯的**(退路保留要求四張表同源);**建了卻假裝能用**更錯。

### 驗收標準

1. **8 支測試由紅轉綠**:
   - `test_migration_0002_up_down_up`(三張表出現/消失)
   - `test_message_schema_matches_upstream`(上游 §4.1 欄位齊;**無** email/姓名/密碼欄)
   - `test_message_recipient_sub_has_no_fk`(🔴 斷言外鍵**不存在**,理由見決定①)
   - `test_announcement_read_unique_per_person`(唯一約束,公告不逐人複製列)
   - `test_announcement_read_cascades_on_announcement_delete`
   - `test_unread_count_index_exists`(未讀鈴鐺 30 秒輪詢,這個查詢會跑很多次)
   - `test_category_check_rejects_unknown_value`(真的 INSERT 一筆壞資料看它被擋)
   - 🔴 `test_models_match_migration_schema`(**補 T05 留下的盲點**)
2. 🔴 **`test_models_match_migration_schema` 是本任務最有價值的一支**:
   T05 誠實標註了一個盲點——應用層測試的 schema 來自 `create_all()`,
   而正式環境來自 migration,**沒有任何一支測試在比較兩者**。
   本任務在同一個 PostgreSQL 上開兩個資料庫,一邊跑 migration、一邊跑
   `create_all()`,逐表逐欄比對。
3. `downgrade()` 真的把三張表刪掉(不得是 `pass`;`0001` 的表不得被動到)。
4. `bash tests/run_all.sh` 全綠且測試總數增加。
5. ⚠ **仍為 PG16 演練**:PG15 的 up→down→up 依 T05 的遺留繼續留在 T11。

### 回滾方式

1. **資料層**:`alembic downgrade 0001` 會 DROP 這三張表(不動 `app_user`/`user_role`)。
   現階段可接受(尚未上線、庫是空的);**上線後不得如此回滾**,屆時須先備份。
2. **程式層**:`git revert <T07 commit>` 回到 T05 結案狀態。
3. 本任務**沒有執行期閥門**——它只有 schema,沒有行為。
   建了表而沒有端點讀寫它,對使用者是零影響(T08 才接上)。
4. 不碰 portal、不碰 VM、不碰已建立的 client。

### 與計畫段的偏離(第二條5)

**測試支數 8 → 9**:多的那支是 `test_announcement_schema_matches_upstream`
(計畫段只列了 `message` 那一張的欄位比對,`announcement` 的漏了)。
它同時釘住「`title` 而非 `subject`」——那個刻意的用詞不一致需要一條斷言,
否則日後有人「順手統一命名」不會有任何東西阻止他。

🔴 **計畫段保持原文不改。**

### 為什麼這樣做(關鍵決策)

計畫段已寫的三項(`recipient_sub` 不設外鍵、`announcement_read` 設外鍵、
CHECK 而非 PG enum)都照計畫執行,結果段不重複。以下是**執行中才決定的**:

**① 索引開了兩個而不是一個。** `(recipient_sub, is_read)` 給未讀鈴鐺,
`(recipient_sub, created_at)` 給收件匣列表排序。兩個查詢的形狀不同,
共用一個索引其中一個一定退化成排序——而**在資料少的時候兩者都很快**。

**② `subject` / `title` 用 `String(255)` 而 `body` 用 `Text`。**
標題超長是**使用者輸入問題**,應該在 API 層回 400(清楚的錯誤,T10);
內容超長是**正常情況**,不該讓資料庫報錯。兩者的失敗模式不同,型別也就不同。

**③ `models_engine` 用第二個資料庫,不用 PG 的 schema 隔離。**
`create_all()` 與 migration 都不帶 schema 名,要用 schema 隔離就得改
model 或動 `search_path`——那會讓測試環境與正式環境的建法**不一樣**,
而這支測試的全部價值就在於「兩種建法要一致」。

### 測試結果(紅 → 綠的證據)

**紅:** `python3 -m pytest tests/test_schema.py -q` → `9 failed, 1 passed`
(唯一那個 pass 是 schema 比對——當時兩邊都只有 T05 的兩張表,所以確實一致)。

**綠:** `bash tests/run_all.sh`(先 `eval "$(bash tests/pg_local.sh start)"`)
→ 文件層 **40 過 / 0 敗**、pytest **71 passed**,合計 **111 項全綠**
(T05 結案時 101 項,+10)。

**突變檢查 9 項,全部被抓到**(明細見 `docs/TDD測試計畫表.md` §5.6)。
其中兩項是 T07 新增的防線,在此之前**沒有任何東西會發現**:

| 突變 | 在 T07 之前會發生什麼 |
|---|---|
| migration 漏一個欄位(model 有、migration 沒有) | 本機測試全綠(用 `create_all()`),**部署後少一個欄位** |
| `downgrade` 順手刪掉 `app_user` | 降一級時把所有人的身分與角色一起刪掉 |

### 🔴 兩項發現

**1. 上游的資料模型有一個我方無法實作的欄位值。**
`announcement.audience` 上游寫「`all` / **群組**」,而群組定向需要 `groups` claim
——我方 client **刻意沒有申請**(T03 申請書〈貳〉明載不申請 `email`、不申請 `groups`)。
處理:欄位照上游建、CHECK 擋在 `all`、註釋標明要開放須先向 portal 申請 §4.2a **L2**。
⚠ **建了欄位卻假裝能用比不建更糟**:發布端會以為自己設定了收件範圍,
而實際上每一則都送給所有人——而那件事在畫面上完全看不出來。

**2. 兩張表對「sub 要不要設外鍵」給出相反的答案,而兩邊都是對的。**
`message.recipient_sub` 不設(推送必須能推給從未登入過的人),
`announcement_read.user_sub` 要設(標已讀者必然已登入過)。
這在日後看起來會像不一致,所以**兩邊的註釋都寫了對方的理由**,
而且各有一支測試釘住——包含一支**斷言外鍵不存在**的。

### 對現有資料的實際影響

🟡 第二條 migration,但**不動任何既有資料**:只有 CREATE TABLE,
`0001` 的 `app_user` / `user_role` 一欄未動(有測試斷言降級時它們必須留著)。
未動 portal、未動 VM、未動已建立的 client。

⚠ `downgrade` 會 DROP 這三張表。現階段可接受(尚未上線、庫是空的);
**上線後不得如此回滾**,屆時須先備份。

### 遺留問題與後續建議

1. 🔴 **PG15 演練仍未做**(承 T05 的遺留)。本機只有 PG16.13。留 T11。
2. **`push_dedup` 表刻意不在本任務**。T14 的 `Idempotency-Key` 去重需要一張
   `(azp, key, message_id, created_at)`,那是 T14 的 `0003`——本任務照任務表
   只做三張表,不擴張範圍。
3. ⚠ **`thread_id` 建了但階段一不用**(人對人是階段二)。它現在沒有索引;
   T15/T16 真的做對話串時要補 `(thread_id, created_at)`,否則「展開對話」
   會是全表掃描。
4. **`source_app` 目前 nullable 且無外鍵/無 CHECK。** T14 會建 `source_app` 對照表
   (以 `azp` 為主鍵,見覆函〈壹〉Q2),屆時要決定是否加外鍵——
   ⚠ 加了的話,一個被停用的來源會讓它**過去的通知也讀不出來**,要謹慎。
5. 💡 `test_models_match_migration_schema` 刻意不比對型別字串(等價但不同名的
   表示會產生假紅燈)。若日後想加,建議只比對「型別家族」(整數/字串/時間)
   而不是完整字串。
