## 計畫段(動工前寫妥,第二條2)

### 🔴 這一列補的是一個「所有文件都假設它已經存在」的東西

`docker-compose.yml` 第 15 行寫著:

```
image: ghcr.io/fttp0165/cats-inbox-api:0.1.0
```

而**那個映像不存在**。沒有任何 workflow 建它、沒有任何任務提到它。
T01 建了 `Dockerfile`、compose 引用了映像、T11 的驗收假設 VM 上
`docker compose up -d` 拉得到它 —— **中間那一步從頭到尾沒有人管**。

🔴 **這個缺口的形狀**:每一份文件都是對的,每一個任務也都完成了,
而把它們接起來的那一步不在任何人的清單上。
⚠ 症狀會在 **T11 的低峰窗口**當場出現(`docker compose up -d` → manifest unknown),
而那是最不該發現這件事的時刻 —— 全 VM 唯一的 gateway 正在等著 reload。

### 目標

1. `.github/workflows/release-image.yml`:**推 tag 才建**,推到
   `ghcr.io/fttp0165/cats-inbox-api:<版本>`;
2. 🔴 **打 tag 前的三道一致性檢查**做成 workflow 裡會失敗的步驟,不是靠人記得;
3. `docs/發版SOP.md` + `.html`:把憲法第八條(title + 四段 content)變成
   一份**照著做就會對**的清單;
4. 測試釘住上面每一項。

### 🔴 三道一致性檢查,每一道都對應一種「不會有錯誤訊息」的說謊

| 檢查 | 不做的後果 |
|---|---|
| git tag `v0.1.0` **==** `app/__init__.py::__version__` | 第八條4:版本號會顯示給使用者(`/inbox/health`、頁尾),**tag 與常數不一致等於說謊**,而換版驗證也會判錯 |
| `docker-compose.yml` 的映像 tag **==** `__version__` | 改了常數而忘了 compose → **部署的是舊映像**,而它的 health 回報舊版本,所以**看起來完全一致**;你以為換版成功了 |
| workflow 推的映像名 **==** compose 引用的映像名 | 建一個、部另一個。這個會在 `docker compose up` 當場報錯(算是有訊息),但錯在低峰窗口 |

🔴 **一律不推 `latest`。**(平台紅線:production 不用 `latest` tag。)
`latest` 讓「同一個 tag 在不同時間指向不同東西」,而回滾時你**不知道要回到哪裡**。

### 影響範圍

| 對象 | 影響 |
|---|---|
| 資料庫 / 既有 API / UI | 🟢 完全不動(純建置與文件) |
| GitHub Actions | 🟡 新增一個 workflow;**只在推 tag 時跑**,不影響每次 push 的 CI |
| portal / VM / gateway | 🟢 不動 |

⚠ **CI 額度**:Docker 建置比 pytest 慢得多。本 workflow **只在推 tag 時觸發**
(不是每次 push),所以次數是「發版次數」而非「commit 次數」。
🔴 而 portal 的 CI 正因額度用盡而紅了一週(2026-08-24 查明)——
本專案的 workflow 若日後也吃到額度,症狀會是**發版當下才發現建不出來**。
故 SOP 第一步就是「確認 Actions 額度」。

### 驗收標準

1. workflow 存在,`on: push: tags: ['v*']`(**加** `workflow_dispatch` 供手動補建);
2. 🔴 **不含 `latest`**;
3. 三道一致性檢查各自是一個**會讓 workflow 失敗**的步驟;
4. `permissions` 最小化(`contents: read` + `packages: write`),不用預設全開;
5. `docs/發版SOP.md` + `.html` 存在,含第八條的 **title 格式**與 **四段 content**,
   且登記進 `render_docs.py` 的 `TARGETS` 與 `test_docs.sh` 的三份清單;
6. 🔴 **誠實標註**:本任務**無法在此環境實際建置**(無 docker daemon、無 GHCR 憑證)
   —— workflow 的「真的跑過一次」留在**第一次發版**,不得宣稱已驗證;
7. `bash tests/run_all.sh`(起本機 PG)全綠 + 突變檢查逐項確認。

### 回滾方式

純新增一個 workflow + 一份文件 + 測試。`git revert` 即可。
⚠ 回滾後回到現狀:**映像仍然沒有人建**。

### 為什麼這樣做(關鍵決策)

**① 只在推 tag 時建,不在每次 push 建。**
Docker 建置比 pytest 慢得多,而 **portal 的 CI 正因 Actions 額度用盡紅了一週**
(2026-08-24 查明)。那種故障的症狀是「發版當下才發現建不出來」。
⚠ 仍保留 `workflow_dispatch`:tag 推了而建置失敗時要能補建,
否則只能再發一個 patch 版(第八條5)。

**② 三道一致性檢查做成會失敗的步驟,不是靠人記得。**
其中第二道(compose 的 tag == `__version__`)擋的是**最安靜的那種錯**:
改了常數而忘了 compose → 部署的是**舊映像**,而它的 health 回報**舊版本**,
所以兩者「看起來完全一致」,而你以為換版成功了。

**③ 推之前先把映像跑起來驗。**
「建得起來」與「跑得起來」是兩件事。少了這一步,壞掉的映像會被推到 registry,
而發現的時機是 VM 上 `docker compose up -d` 之後 —— 也就是**低峰窗口裡**。
冒煙刻意**不給任何 OIDC 設定**:健康檢查不查 DB 也不需要 IdP,
所以它必須在「什麼都還沒設定」時就是 200(T01 的回滾閥門)。

**④ 順手把 `test_docs.sh` 的三份手寫清單改成自動產生。**
D01 已經記過一次:**新文件不登記進守門的清單,`--check` 會全綠**。
而那份清單原本手寫三次 —— 新增一份文件要記得改**四個地方**。
自動產生之後,「新增文件」與「納入守門」變成同一個動作。
⚠ 並立刻斷言數量下限:解析失敗會讓清單變空,而**空清單的迴圈是全綠的**。

### 測試結果(紅 → 綠的證據)

**紅:** 新測試先寫,首次執行 **5 error + 1 failed / 1 passed**
(error 是 workflow 檔不存在)。那 1 個通過的是
`test_compose_image_tag_matches_version_constant` —— compose 與常數本來就都是
`0.1.0`,它釘的是**既有的正確狀態**,不是 T10c 做出來的。

**綠:** `bash tests/run_all.sh`(**已起本機 PostgreSQL**)→
文件層 **51 過 / 0 敗**(登記 SOP 前 45)、pytest **180 passed / 0 skipped**,
合計 **231 項全綠**。

**我在本機能驗的兩件事(已實測):**

```
sed -n 's/^__version__ = "\(.*\)"$/\1/p' app/__init__.py      → 0.1.0
sed -n 's|^ *image: .../cats-inbox-api:\(.*\)$|\1|p' compose  → 0.1.0
✅ 兩者相符
每個 run: 區塊 bash -n → 2/2 通過
```

**守門看得到新文件**(照 D01 的做法故意改壞一次):
```
在 docs/發版SOP.html 尾端加一行 → --check
  ✅ 守門看得到新文件(--check 紅)
還原 → ✅ --check 綠
```

**突變檢查:15 項全被抓到。** ⚠ 但這是**修掉一個測試洞、修正兩處工具錯誤之後**的數字。

### 🔴 一項測試洞 + 兩項工具錯誤

**測試洞:SOP 的四段檢查驗的是「字串在不在全文裡」,不是「有沒有那個標題」。**
把 `## 部署注意` 改成 `## 其他` 之後那一條仍然綠 ——
因為「部署注意」四個字在 §4 的說明文字裡也出現過。
已改成驗 `## 部署注意`(帶標題標記)。
🔴 **與 T09b、T10b 那幾個洞同型:斷言的粒度比它宣稱保護的性質粗。**
這是連續第三輪出現同一種形狀。

**工具錯誤兩處(守門的警示行都有講出來):**

| 我做的 | 實際上 |
|---|---|
| 把 `if [ -z "$X" ]; then` 改成缺 `]`,當成語法錯 | **`bash -n` 認為那合法** —— `[` 是命令不是語法,缺 `]` 是執行期錯誤。改成刪一個 `fi` 才是真的語法錯 |
| 用 `pytest tests/test_docs.sh` 當選擇器 | pytest 收不了 `.sh`,回 **rc=4** —— 而 T10 加的守門正確地報「選擇器選不到任何測試」,沒有算成「抓到」 |

⚠ 第二項證明 T10 那道守門有用:**若沒有它,這一項會顯示成假 ✅。**

### 遺留問題與後續建議

1. 🔴 **workflow 從未在真的 Actions 上跑過**(本機無 docker daemon、無 GHCR 憑證),
   `ghcr.io/fttp0165/cats-inbox-api:0.1.0` **目前仍不存在**。
   **第一次發版就是這份 SOP 的第一次演練** —— 已寫進 SOP §0。
2. ⚠ **`packages: write` 能否推到 GHCR 還沒驗過。** repo 可能需要在
   Settings → Actions → Workflow permissions 允許,或 package 需先建立並連結 repo。
   這一項只能在真的推一次時才知道。
3. ⚠ **Actions 額度未知。** portal 因額度用盡紅了一週;本 repo 的 CI 目前是綠的,
   但沒有人看過剩餘分鐘數。SOP 第 1 步就是確認它。
4. 💡 `tests/test_docs.sh` 的清單現在自 `TARGETS` 產生,而 `TARGETS` 仍是手寫的。
   下一層(自動掃 `docs/*.md`)不做:並非每份 md 都該進文件鏈(dev-log 就不該),
   所以那份名單**應該**是人選的。
