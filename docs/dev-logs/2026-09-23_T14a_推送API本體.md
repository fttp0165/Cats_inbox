## 計畫段(動工前寫妥,第二條2)

### 目標

把 portal 2026-08-18 核定的寫入型 S2S 規格(契約 §11.7 第一案)與我方 2026-08-24 對三問的答覆
(`docs/契約對齊盤點_v3.3.md` §4 Q2/Q3)做成**可離線驗證**的實作:

1. `POST /inbox/api/v1/notifications` —— 驗 S2S token(RS256/JWKS/`iss`/`aud`/`exp`±30s)、

2. 來源登記表 `source_app`(`azp` → 顯示標籤 + 啟用旗標)與管理後台 `/inbox/admin/sources`
   (Q2 答覆:「新增來源=管理後台加一列;可停用單一來源而不動程式」);
3. 去重收據表 `push_receipt`;migration **`0003`**;
4. 來源接入指南 `docs/來源接入指南.md` + HTML(給第一個來源系統的團隊照做)。

### 🔴 為什麼現在做,以及為什麼把 T14 拆成 T14a / T14b(第一條4)

任務表 T14 的依賴欄寫著「**第一張憑證待 DI-4 立案**」。但逐條看驗收,**六支規格測試沒有一支需要真的憑證**
—— 它們要的是一張「由 IdP 簽、帶某些 claims」的 token,而 T04 在 client 核發**之前**就用假 IdP 簽出
這種 token 把登入流程做完了。真正需要憑證的只有「**接入第一個來源**」那一步。

這與 T11 拆成 T11a/T11b 是同一個形狀(任務表 v1.21):**阻塞條件不同,合成一列會讓能做的那一半

⚠ **誠實標註(第二條3)**:本任務是新功能 + migration,屬第二條3 的「大任務」。依本專案 T05/T07/T09 的既有做法,

### 驗收標準

六條來自任務表 T14 與 `docs/TDD測試計畫表.md`(portal 2026-08-18 核定);其餘是本任務自加的。
**每一條都對應一種不會有錯誤訊息的失敗:**

| # | 驗收 | 壞掉時的症狀(為什麼要有這一條) |
|---|---|---|
| 1 | 無 token / **使用者的 id_token** / 使用者的 access token / 錯 `aud` / 過期 / HS256 → **401** | 🔴 id_token 的 `aud` **正好就是 `cats-inbox`** —— 只驗 `aud` 的話,任何登入過的人拿自己的 id_token 就能以系統身分發通知 |
| 2 | `aud` 對但缺 `notification:push` → **403**(不是 401);scope 比對是**整詞** | §11.5:401/403 混用,呼叫方查不出是憑證錯還是授權不足;子字串比對的話 `notification:pushall` 也算 |
| 3 | 未登記 / 已停用的 `azp` → **403**;請求帶內網來源位址照樣 403 | §11.5 第 3 條:「**內網不是身分**」 |
| 4 | `X-User-Id` 缺 / 非 UUID / 等於呼叫方自身 → **400 且零列** | portal 加嚴條件:「缺就當系統發出」會讓稽核鏈在最需要的時候恰好是空的 |
| 5 | 同 `Idempotency-Key` 24h 內重送 → **200、同一 id、零新列**;缺 key → 400;超窗 → 201 新訊息 | 重試造成同一則通知出現兩次;超窗拒收則讓一個月後的重跑**靜默失敗**(Q3) |
| 6 | body 帶 `source_app` → **被忽略**,以 `azp` 查表的標籤為準 | 能自稱來源 = 能冒充任何系統發通知,而通知帶著平台的官方外觀 |
| 7 | 同 key、**不同內容**(24h 內)→ **422 且零新列** | 呼叫方把 key 重用在另一個事件上時,第二則會被當成重送**默默丟掉** —— 而「通知沒送到」是本系統最糟的失效模式 |
| 8 | key **以呼叫方為範圍**:兩個來源用同一把 key 互不影響 | 否則 A 系統的 key 會讓 B 系統的通知被「回放」成 A 的那一則 —— 內容跨來源外洩 |
| 9 | `recipient_sub` 非 UUID 形狀 → **400 且零列**;大寫 UUID 正規化成小寫 | 傳 email 或帳號名進來會**回 201**,而那則訊息**沒有任何人看得到**(收件匣以 `sub` 比對)—— 靜默遺失 |
| 10 | 外部 `action_url` 經推送端點 → **400 且零列** | T10 把關卡設在 `repo.create_message()`,理由正是「T14 動工時驗證是附帶工作,最容易忘」—— 這條證明 T14 **真的穿過它** |
| 11 | **先認證、後讀 body**:無 token + 壞 JSON → **401** | 否則未認證的呼叫方拿到的是 400/422,而且能用它探測 payload 格式 |
| 12 | 推送的訊息,**收件人登入後真的看得到**,標籤是登記表的 label | 只驗 201 的話,「寫到別人名下」「寫到錯的欄位」都是 201 |
| 13 | log 有 `azp` / actor / `message_id`;**沒有**主旨、內容、token 全文 | A.3 紅線;個資或 token 落進 log **沒有任何人會發現** |
| 14 | 🔴 **列舉式守門:所有寫入路由,匿名請求一律 401/403** | A.3「**無驗證的推送端點不得部署**」目前只是一句話 —— 列舉之後,下一個忘了掛認證的寫入端點會在 CI 紅 |
| 15 | 來源後台:非 admin **403**;登記/停用**即時生效**;壞值 400 零列;表單帶 CSRF(T10b 的列舉守門自動涵蓋) | 停用要等重啟才生效的話,「可停用單一來源而不動程式」(Q2)就是假的 |
| 16 | 並行的同 key 請求:第二個撞唯一約束 → **回放 200,零重複** | 先查後寫之間的空窗,在真實重試風暴裡一定會被撞到 |
| 17 | migration `0003` up→down→up(CI 的 **PG 15**);降級**不動** `0001`/`0002` 的表;`(azp, key)` 唯一約束在 PG 上**真的擋** | 降級手誤帶走 `message` = 刪掉所有人的通知 |

### 🔴 設計決定(先寫下,因為它們會被誤讀成疏漏)

1. **收據表不做每日清理** —— 與 2026-08-24 答覆 Q3 的**內部**描述不同,**對外語意不變**
   (24 小時、超窗視為新訊息)。理由:①本服務刻意沒有排程器(A.1 極簡棧:無佇列、無背景工作),
   「每日 DELETE」需要一個不存在的東西去跑它;②收據同時是 **`X-User-Id` 的持久稽核紀錄**
   —— portal 加嚴那一條的理由正是稽核鏈,**每日刪收據就是每日刪稽核**。
   改為:窗口**以時間比對**判定;收據隨 `message` 保留(外鍵 `ON DELETE CASCADE`,N3 定保留期時一併處理)。
   超窗重用同一把 key → 覆寫該列收據指向新訊息(舊的關聯仍在 log)。→ **回寫 Q3**(第二條5)。
2. **同 key 不同內容回 422**(IETF `draft-ietf-httpapi-idempotency-key-header` 的建議碼),不回放。
   回放會讓呼叫方拿到 200 而**第二則通知不存在**。
3. **`recipient_sub` 也驗 UUID 形狀** —— 核定規格只要求驗 `X-User-Id`;加這一條的理由見驗收 9。
   前提與核定規格相同:平台的 `sub` 是 Keycloak 的 UUID(`X-User-Id` 的 UUID 規則本身就建立在它上面)。
4. **token 的 `azp` 等於我方自己的 client_id → 401**:那是使用者登入流程簽給我方的 token
   —— 我方 client 的 service account **已確認停用**(T03 回讀驗證),不可能是服務憑證。
5. **`typ` 必須是 `Bearer`** —— 這是驗收 1 裡「使用者 id_token」那一格**唯一**擋得住的地方:
   Keycloak 的 id_token 是 `typ: ID` 而 `aud` 就是 `cats-inbox`。
6. **body 在認證之後才讀**,且**所有輸入錯誤一律 400**(不是 FastAPI 預設的 422)——
   對齊 `docs/開發計畫書.md` §3.4 的錯誤語意;**422 只留給決定 2**,讓它有單一意義。
7. **scope 名稱與 24h 窗口寫死成常數**,不從設定讀 —— 與 `ROLE_CAPABILITIES`、`SITE_ORIGIN` 同一個理由:
   設定可以被改寬,而改寬沒有症狀。
8. **來源標籤以「快照」寫進 `message.source_app`**:改標籤不回溯既有訊息(與信件的寄件人顯示同理)。
9. 🔴 **不對 `message` 加欄位**(稽核放在 `push_receipt.actor_sub`)—— 上游 §2.1 的退路是「**搬四張表**」;
   在 `message` 上長出 S2S 專用欄位,搬表就變成一次資料遷移。兩張新表是 S2S 路徑專用的,
   併回 compliance 時由其內部呼叫取代,不需要搬。

### 🔴 對現有資料的影響

🟡 **加表**:`CREATE TABLE` ×2(含索引、唯一約束、外鍵)。**不動任何既有表的欄位、無 UPDATE、無刪除。**
VM 上的庫停在 `0002`;`0003` 要等下一次發版才會在 VM 上跑,**本任務不碰 VM**。

### 回滾方式

1. 程式:`git revert` 本任務的提交。
2. migration:`0003` 的 downgrade **只刪兩張新表**(測試釘住 `0001`/`0002` 的表留著)。
   ⚠ 上線後回滾前必先備份(共通紅線)——收據表是稽核紀錄。
3. **不必回版的關閉方式**:推送端點在「沒有任何啟用中的來源」時等於全拒(deny-by-default),
   上線後可在來源後台**停用全部來源**,秒級關閉。
