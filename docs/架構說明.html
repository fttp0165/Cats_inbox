1. 一句話

把散在各系統的通知收到一個地方,讓人在統一入口看得到未讀。

不做即時聊天,不做推播,不做附件。刻意極簡:無 Redis、無訊息佇列、無 WebSocket
——未讀鈴鐺用 30 秒輪詢。

2. 商業邏輯:一則通知的一生

2.1 為什麼是兩種形狀,不是一種

messageannouncement + announcement_read
形狀逐人一列一則對多人,已讀才逐人一列
已讀狀態就在那一列上(is_read / read_at)另一張表(有 (公告, 人) 唯一約束)
為什麼每個人的內容不同,本來就要一人一列一萬個人的公告若逐人複製,就是一萬列內容相同的資料

2.2 角色 → 能力:每一格都是寫死的

角色能力怎麼取得
readerread_own(讀自己的訊息 / 標自己已讀 / 看有效公告)✅ 首登自動授
sendersend_message⛔ deny-by-default,管理員指派
announcerpublish_announcement⛔ deny-by-default,管理員指派
adminmanage_roles⛔ deny-by-default(刻意不含 read_own)

🔴 對應表寫成模組層常數(app/authz.py),不是設定檔。
設定檔可以被改寬,而改寬不會有任何症狀——功能上一切正常,
只在有人做了不該做的事時才顯現,而那時已經發生了。

⚠ admin 刻意不含 read_own:管身分與讀信是兩件事。綁在一起會讓
「單獨停用 reader」對管理員失效。管理員也要讀自己的信時,他身上另外有
reader(首登就有)。

2.3 🔴「首登自動授 reader」是一個經核可的偏離,不是預設行為

平台契約的預設是 deny-by-default:首登建號、零角色、看到待開通頁。
本專案向 portal 申請並於 2026-08-18 獲核可偏離,理由是
「reader 的可及集合在定義上恆等於本人資料——deny-by-default 要防的是
拿到別人的東西,而這裡沒有別人的東西」。

核可附四項條件,同列本專案紅線:

條件落點
C1 範圍寫死在自我範圍讀取app/authz.py 的 ROLE_CAPABILITIES
C2 reader 須可由本專案後台單獨停用user_role.enabled(per-user,即時)+ INBOX_AUTO_GRANT_READER(全域,⚠ 需重啟)
C3 以反向測試釘住 C1 並納入 CIreader 寄信 → 403、reader 發公告 → 403
C4 M4 上線一週內回報實測;portal 得單方撤回全域開關關掉即回到全 deny

2.4 🔴 現在做不到的三件事(不寫出來,讀的人會以為現在就有)

做不到的事為什麼要開放需要什麼
公告的群組定向需要 groups claim,而本專案的 OIDC client 刻意沒有申請另向 portal 申請契約 §4.2a L2
收件匣顯示寄件人姓名契約 §4.2a L1 明文:顯示名稱快取不得出現在一般使用者可見頁面portal 的 DI-3 裁決(已排定 M4 上線後與 rf-workorder #14 併案)
各系統推送系統通知寫入型 S2S;§11.7 原本一律不核發✅ 已於 2026-08-18 原則核可;實作是 T14(M5)

⚠ audience 欄位照上游建了,但資料庫 CHECK 把它擋在 all。
理由:建了欄位卻假裝能用,比不建更糟——發布端會以為自己設定了收件範圍,
而實際上每一則都送給所有人,而那件事在畫面上完全看不出來。

3. 技術架構

元件說明網路
cats-inbox-apiFastAPI + Jinja2,prebuilt image、non-root、健康檢查 /inbox/health(刻意不查 DB)cats-edge(external)+ 自家內部網;只 expose 8080,不 publish
cats-inbox-pgPostgreSQL 15只在自家內部網;不上 cats-edge、不對主機發布 port
portal-gateway全 VM 唯一入口路由權威在 cats-portal,改它一律走其 PR

3.1 身分:全部交給 Keycloak

  • Authorization Code + PKCE(S256)、RS256 + JWKS(快取 1h、支援 kid 輪替)。
  • 驗 iss / aud / exp,時鐘容忍 ±30 秒。
  • 401 = 憑證無效;403 = 已認證但無此權限。 兩者不得混用——<br>混用會讓查問題的人分不出「我沒登入」還是「我沒被開通」,而下一步完全不同。
  • 業務庫只存 sub,不存 email、不存密碼。姓名只有一個受限的快取欄位(見 §4)。

🔴 伺服器端主動續期。 access token 只有 300 秒,而伺服器端算繪的 App
不會有前端 JS 幫它 refresh。不做的話症狀是
「登入 5 分鐘後靜默退回未登入,而伺服器零錯誤」。

3.2 登出有兩個方向

方向端點行為
自發登出GET /inbox/logout先清本地 session,再導 IdP 的 end_session
被通知登出(SLO)GET /inbox/oidc/frontchannel-logout免認證、冪等、只准刪、回 204

🔴 front-channel 端點是 IdP 主動呼叫的,那一刻使用者的瀏覽器不在現場
——這就是 session 存伺服器端(而非無狀態簽章 cookie)的唯一理由:
無狀態 cookie 只有瀏覽器有,IdP 通知得到而我方無從作廢。

3.3 資料表(四張)

表內容關鍵約束
app_usersub + display_name(L1 快取,nullable)+ is_active無 email / 密碼 / 姓名欄
user_role(sub, role, enabled)停用是 enabled=false,不是刪列
message逐人一列的通知🔴 recipient_sub 不設外鍵
announcement / announcement_read公告 + 逐人已讀(公告, 人) 唯一;user_sub 有外鍵 CASCADE

🔴 兩張表對「sub 要不要設外鍵」給出相反的答案,而兩邊都是對的:

  • message.recipient_sub 不設:推送 API 必須能推給從未登入過 inbox 的人<br>(新到職的同事、或 PLM 那 50 位沒有 email 的測試工程師)。設了外鍵,<br>那些推送會被資料庫擋掉,而症狀是「通知沒送到」——收件人自己不會知道。
  • announcement_read.user_sub 要設:要標記公告已讀,你必然已經登入過。

4. 個資與安全:這個系統的第一風險

站內信是使用者輸入直接展示給其他人看,所以本專案在平台紅線之上自我加嚴:

紅線為什麼落點(T10 已落地)
body 一律純文字儲存與輸出(輸出必跳脫)stored XSS 是第一風險;同源之下一次 XSS 可觸及 IdP✅ Jinja2 預設跳脫,四支模板一律 {{ }} 不用 `\safe`
action_url 只接受同站值,否則 400 拒收站內通知天生長得「可信」,是現成的釣魚載具✅ 寫入側與輸出側各驗一次;14 則反例
訊息主旨與內容不進 loglog 只記 id、sub、事件類型✅ 全流程抓 stdout 斷言;且每行為單行 JSON
sender_sub 一律由後端自 token 取;收件權限後端判定前端傳入的身分欄位一律不採信✅ 請求模型裡沒有那個欄位(不是收下來再忽略)
嚴格 CSP + 逐請求 nonce(契約 §4.10)沒有 CSP 時,一次注入就能載入外部腳本✅ middleware 統一加;守門列舉所有 HTML 路由
推送 API 必須驗 S2S token無驗證的推送端點不得部署到正式環境⏳ T14(M5)

🔴 兩件 T10 才發現、而「做了一半」時完全沒有症狀的事:

  1. action_url 的白名單必須在寫入側與輸出側各驗一次。 寫入側的驗證是 T10<br>才加的 —— 在它之前寫進去的列、日後手動改過的列、被入侵寫進去的列<br>都繞過了它。輸出側是唯一能保護既有資料的地方。
  2. 嚴格 CSP 連 style="…" 屬性也擋,而 nonce 只對「元素」有效。<br>也就是說「<style> 帶了 nonce」不等於「樣式會生效」。本專案原有 5 個<br>行內樣式屬性,全部改成 class —— 不改的症狀是版面走鐘而伺服器零錯誤。

⚠ frame-ancestors 'none':本服務不可被 iframe 嵌入。 現行設計是入口頁
「連結」到本服務。若改成嵌入,必須先改那一行,否則 iframe 是一片空白而零錯誤訊息。

4.1 顯示名稱:唯一的具名例外,而且範圍很窄

app_user.display_name 是契約 §4.2a L1 的具名例外:

  1. 僅得自本人登入 token 取得(程式裡只有一條寫入路徑,以源碼檢查釘住);
  2. 僅供管理後台顯示——一般使用者可見的頁面與 API 回應都不得出現;
  3. 不進 log;4. nullable;5. 附整批 + 單筆清除工具;
  4. 授權判定一律不讀它(以源碼層 AST 檢查釘住,不靠行為測試)。

⚠ 第 2 點的「API 回應」是實測補上的:原本只驗了 HTML 頁面,
而往 JSON 回應加一個姓名欄位測試照樣綠——模板沒有算繪它,
但前端 JS 拿得到,而契約禁的是「出現在一般使用者可見的面」。

5. 使用者介面概念

5.1 五個畫面各自解決一件事

畫面解決什麼狀態
入口鈴鐺讓人不必進來就知道有沒有新的⏳ T12(portal 側)
收件匣頁看自己的訊息與有效公告、點開即已讀✅ T08 + T09
公告發布頁讓 announcer 不必用 curl 就能發公告;時間欄位由頁面宣告是台北時間✅ T09b
待開通頁🔴 解 deny-by-default 的雞生蛋:第一個使用者無人能開通他,故頁面顯示他自己的 sub 讓他自助交給管理員✅ T05
已登出頁讓人看得出登出成功了✅ T06
角色後台指派角色;顯示名稱只在這一頁出現✅ T05

5.2 三條 UI 紅線

  1. 零外部 CDN(契約 §4.10):Bootstrap 5 本地託管。<br>⚠ 檔案不在 StaticFiles 掛載目錄下時 app 不會送出去 ——<br>症狀是「整頁沒有樣式」而伺服器零錯誤(portal 2026-08-03 踩過)。
  2. light 主題寫死,不做 prefers-color-scheme 深色切換(憲法第四條 1/2)。<br>⚠ T10 起不得使用行內樣式屬性 —— 嚴格 CSP 會擋掉它,而 nonce 只對元素有效。<br>要加樣式一律加 class 到頁面的 <style> 區塊(它帶逐請求 nonce)。
  3. 階段一零人名:寄件人一律以 source_app 標籤呈現。<br>這不是「還沒做」,是 DI-3 裁決前的規格。
  4. 表單一律零 JavaScript(T09b)。CSP 是 default-src 'none' 且刻意沒有<br>script-src,所以腳本會被靜默擋掉。因此時區不靠 JS 補、驗證全在伺服器端。<br>🔴 而時間欄位的時區必須寫在畫面上 —— datetime-local 送出的值不帶時區,<br>我方 API 拒收不帶時區的值,所以由頁面宣告(台北時間 UTC+8)後端再補位移。<br>宣告不是猜:API 拒收是因為呼叫方可能在任何時區,而頁面已經告知使用者。

⚠ 已知缺口三項(都不會有錯誤訊息,故寫在這裡而不只寫在任務表):

  1. 收件匣列表沒有分頁(limit=50)。這不是效能問題,是功能缺口<br>——第 51 則就看不到了,而它在測試資料只有兩三筆時完全看不出來。
  2. 🔴 角色後台的兩個 POST 表單沒有 CSRF(清除顯示名稱、指派角色)。<br>它們在 T05 就存在,而當時本專案還沒有任何 CSRF 機制 —— 這不是新破的洞,<br>是一直開著而沒有人注意到,直到 T09b 做第一個表單時才浮現。已列為 T10b。
  3. 入口鈴鐺不數公告。unread-count 那個端點的名字就叫 messages,<br>T09 刻意沒有改它的語意;若 T12 不處理,發出去的公告在入口頁零信號。
