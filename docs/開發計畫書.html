0. TL;DR

  1. 做什麼: 全平台訊息中心。各系統把事件推進來、管理員發公告、使用者從入口進收件匣;未讀鈴鐺 30 秒輪詢。收件人一律 IdP 的 sub。
  2. 選址已變更: 由設計規劃 v1.3 的「掛 compliance_system」改為獨立 repo/容器(Benny 2026-08-15 指示,DI-1);功能設計沿用,選址理由與回寫義務見 §1.2。
  3. 怎麼上: 六個里程碑——M1 骨架 → M2 SSO → M3 通知核心(公告先行)→ M4 掛上入口 → M5 S2S 推送(系統通知開通)→ M6 人對人(階段二)。依賴最少的先上線:公告不依賴任何他系統。
  4. 閘門現況(2026-08-18 更新): DI-2 開通偏離 ✅ 已核可(附四條件);寫入型 S2S ✅ 已獲原則核可(§11.7 第一案,規格已定);DI-3 顯示名稱 ⏳ portal 不現在裁決,俟 M4 後與 rf-workorder #14 併案。仍卡在別人手上的只剩一件:client 尚未在 VM 建立(腳本已備妥,portal EXT-11)。
  5. 估時: MVP(M1–M4,公告中心上線)約 35–47 小時;M5 再 +7–10 小時;M6 再 +13–19 小時(不含裁決與 portal 側等待)。

1. 背景、上游與選址變更

1.1 這個系統是什麼(沿用設計規劃 v1.3 §1)

類型說明納入
系統通知工單指派、TRF 退回、審核待處理等流程事件自動通知✅ 階段一(M5 開通)
公告 / 廣播管理員發全站公告(維護通知、政策更新)✅ 階段一(M3–M4 先上線)
人對人站內信同事互寄訊息、對話串✅ 階段二(M6,前置 DI-3)
即時聊天已讀狀態、線上狀態、WebSocket 推送❌ 不做(CP 值低,沿用 v1.3 結論)

設計規劃 v1.3 的關鍵前提「需要統一身分(SSO)」已成立:IdP(Keycloak realm sporton)已上線,upload-program、sporton_core、portal-admin 三個 App 已端到端接入(SSO 契約 §9 登記表)。收件人自始採 sub,不需任何帳號對應表。

1.2 選址變更(DI-1,已定)——本計畫的第一個決策

設計規劃 v1.3 §2 當時選「掛 compliance_system(新增 notifications app)」,並把「獨立通知微服務」標為「未來再議」。2026-08-15 Benny 指示成立獨立 repo Cats_inbox,在 cats_portal 服務下提供站內通訊——「未來」已到,本計畫書據此改為獨立服務。

變更理由(記錄下來,供日後檢視這個決策):

  1. compliance_system 仍在開發中(portal 憲法系統清單現況欄)。把全平台的訊息中心綁在一個開發中系統的發版節奏上,通知的可用性會被 compliance 的迭代綁架;選址變更後 compliance 零配合工作,反而卸下了原方案加在它身上的「訊息中心」角色。
  2. 訊息中心天生是入口級服務:所有系統都推事件進來、入口首頁的鈴鐺打它的 API。獨立的生命週期與回滾邊界,符合平台「各系統獨立 repo/容器、互通一律 HTTP API」紅線。
  3. 當時反對獨立服務的理由是「對單人維運過度設計」。緩解:技術棧刻意極簡(FastAPI + PG15,無 Redis、無佇列、無 WebSocket,輪詢不推播),部署形態照抄 upload-program 已驗證的模式(同為 FastAPI 獨立服務、confidential client、子路徑掛載)。
  4. 退路保留:資料模型與 API 契約沿用設計規劃 v1.3 §4–§5 原案。若獨立維運被實測證明過重,併回 compliance 的遷移成本=搬四張表+改 upstream,原案隨時可退。

🔴 回寫義務(憲法第二條5 同型): 選址是設計規劃 v1.3 的實質內容,變更必須回寫該文件並升版,不得讓 portal repo 留著已知過期的選址結論——列為 T02(cats-portal 側 PR,由本專案發起、portal 收錄)。

2.3 契約缺口(誠實列出——這三件事現行契約沒有給路,不得假裝已解)

  1. 人對人寄件人顯示名稱(擋階段二,DI-3)。 ⏳ 2026-08-18 portal 回覆:不現在裁決,俟本專案 M4 上線後與 rf-workorder #14 併案評估(理由:它要新增契約條文,而在資訊最少時定會定出比需要更寬的條文,寬的條文收不回來)。我方提案方向已依契約 v3.1 的判準修正為「另立一節」而非「§4.2a 增訂級別」——因同儕可見是第三種失敗模式(錯了不會被管理員或寄件端發現,而是被平台上另一個人看到)。<br>以下為原始論證,保留備查:§4.2a L1 允許快取 name,但明文「僅供管理後台顯示;不出現在一般使用者可見頁面、不進 API 回應」——收件匣對一般使用者顯示寄件人姓名不在現行契約允許範圍,而只顯示 sub 的站內信沒有可用性。階段二動工前必須向 portal 送申請取得裁決(援 upload-program「申請書→裁決文件」前例;§4.2a 自己也預告了重開條件:「第二個 App 出現同樣需求,那就不是特例,而是本條需要重新設計」——cats-inbox 就是那個第二個 App)。提案方向見 §5 DI-3。未裁決前,M6 不動工;階段一(系統通知+公告)刻意設計成零人名需求(§3.6)。
  2. ~~S2S 憑證(擋系統通知推送,M5)~~ → 已改變性質(2026-08-18 更新)。<br>🔴 原敘述「S2S 章節未定稿」已失效:章節早在契約 v3.0(2026-08-15) 就定稿為 §11。<br>真正擋住 M5 的是 §11.7 的一條既存禁令:「寫入型 S2S 一律不核發」——而本服務的推送 API 正是寫入型(各系統把通知寫進我們)。<br>這兩者在計畫書上長得一樣,在排程上完全不同:前者是等別人寫規格,後者是要一個裁決。<br>✅ 2026-08-18 已獲 portal 原則核可(§11.7 第一案),規格已定:scope notification:push、<br>必帶 X-User-Id(須驗形狀且不得等於呼叫方自身,否則 400)與 Idempotency-Key(去重)、<br>source_app 一律由 service client 身分推導不得取自 body、逐端點驗 scope 不只驗 aud。<br>⏳ 仍未有任何憑證核發——第一張要等第一個來源系統(DI-4)立案時照 §11 走。
  3. 開通政策(DI-2)。 ✅ 2026-08-18 portal 核可(附四條件,見 §5 DI-2 列)。以下為原始論證,保留備查。 契約 §4.3/4.4 的 deny-by-default 是 MUST:首登零角色→403 待開通。對 inbox 而言「讀自己的收件匣」是自我範圍資料(只能讀 recipient_sub == 自己),逐人手動開通=206 人排隊等著看通知,體感像壞掉(§4.2a D7-7 裁決自己也記載了這個代價)。提案:讀自己收件匣+標已讀=首登自動授 reader 角色;人對人寄信、公告發布維持 deny-by-default 手動開通(防自助註冊帳號濫發)。此為對契約 MUST 的偏離,需 portal/Benny 核可(前例:upload-program 首頁落地頁是「唯一經核准的偏離」,程序可循)。未核可前照契約全 deny,不先斬後奏。

3. 系統設計概要

3.1 架構

三段資料流(沿用設計規劃 v1.3 §3):① 事件來源(各系統走 S2S、使用者/管理員走 JWT)推送 → ② cats-inbox 存 → ③ 前端輪詢顯示未讀鈴鐺與收件匣。

3.2 容器與網路

容器內容網路port
cats-inbox-apiFastAPI + Jinja2(伺服器端算繪),prebuilt image、non-root、健康檢查 /inbox/health(不查 DB)、restart policycats-edge(external)+ 自家內部網只 expose 8080,不 publish
cats-inbox-pgPostgreSQL 15(平台版本紅線),volume 持久化只在自家內部網不對主機發布

3.3 資料模型(沿用設計規劃 v1.3 §4,微調)

四張表,皆只存 sub,無 email/姓名/密碼欄(唯 app_user.display_name 為 §4.2a L1 快取,限管理後台顯示):

表欄位要點
app_usersub(unique、不可變)、本地角色、display_name(nullable,L1 快取:僅自本人登入 token 寫入、附整批清除工具)、created_at、last_login_at
messageid(UUID)、recipient_sub、sender_sub(null=系統)、category(system/direct)、subject、body(純文字)、action_url(nullable,🔴 同站白名單)、source_app、thread_id(nullable,階段二)、is_read/read_at、created_at(後端產生,不信前端)
announcementid、author_sub、title、body、audience(all;分群留待 N1)、starts_at/ends_at、created_at
announcement_readannouncement_id、user_sub、read_at(公告一則對多人,已讀逐人記,不逐人複製列)

migration 用 Alembic;每條 migration 必附 backward,發版前本機 up→down→up 演練(憲法第八條6)。

3.4 API 契約(沿用設計規劃 v1.3 §5;實作時以 OpenAPI 為權威)

端點認證用途
POST /inbox/api/v1/notificationsS2S token(M5 起)各系統推事件(recipient_sub、subject、body、action_url、source_app)
GET /inbox/api/v1/notifications?unread=1使用者 session/JWT我的訊息列表
GET /inbox/api/v1/unread-count使用者 session/JWT未讀數(鈴鐺輪詢,30s)
POST /inbox/api/v1/notifications/{id}/read使用者 session/JWT標已讀(冪等)
GET /inbox/api/v1/announcements/active使用者 session/JWT目前有效公告
POST /inbox/api/v1/announcements使用者 session/JWT + announcer 角色發公告
POST /inbox/api/v1/messages使用者 session/JWT + sender 角色階段二:寄站內信(sender_sub 一律取自 token)
GET /inbox/health免認證健康檢查,不查 DB
GET /inbox/oidc/frontchannel-logout免認證(§10.3)SLO:清 session cookie、204、冪等

錯誤語意:401=token 無效;403=已認證未授權(含待開通);400=輸入不合法(含 action_url 非同站)。

3.5 權限模型(deny-by-default)

角色能做什麼授予方式
(無角色)只有待開通頁(顯示本人 sub)首登自動建號
reader讀自己的收件匣、標已讀、看有效公告⏳ DI-2:提案首登自動授;核可前=管理後台手動
announcer發公告、管公告有效期管理後台手動
sender(階段二)寄人對人站內信管理後台手動(防自助註冊帳號濫發)
admin派角色、清 L1 快取、看來源系統登記bootstrap 清單(每次登入比對)+ 管理後台手動

鐵則:使用者只能讀 recipient_sub == 自己 sub 的訊息,查別人的回 403;sender_sub/身分欄位一律後端自 token 取,前端傳值不採信。

3.6 UI 原則

  • 伺服器端算繪(Jinja2),base path /inbox/;Bootstrap 5 自行託管(對齊 portal Bootstrap5 導入方向,§4.10 禁 CDN);light 主題。
  • body 純文字輸出、一律跳脫;action_url 僅同站(白名單驗證在寫入時就拒,不是輸出時才擋)。
  • 🔴 階段一 UI 零人名:系統通知顯示 source_app 標籤(如「TRF 系統」),公告顯示「平台公告」——不顯示任何個人姓名,使 §4.2a 缺口(DI-3)不擋階段一。
  • 待開通頁顯示本人 sub 與「找 inbox 管理員開通」指引(§4.3,不是冷 Forbidden)。
