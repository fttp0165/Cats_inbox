cats-inbox 推送 API 來源接入指南

建立日期: 2026-09-23 17:30
最後更新: 2026-09-23 17:30
版本: v1.0

給誰看: 要把系統通知推進站內信的來源系統團隊(第一個是 DI-4 立案的那一個)。
一句話: 用你們自己的 S2S client 以 client_credentials 換一張帶 notification:push 的 token,
POST /inbox/api/v1/notifications,每個事件帶一把 Idempotency-Key 與觸發者的 X-User-Id。
規格權威: portal 2026-08-18 核定(《帳號系統接入契約》§11.7 第一案)+ 本服務 OpenAPI(/inbox/openapi.json)。
本指南與契約衝突時以契約為準;與 OpenAPI 衝突時以 OpenAPI 為準,並請回報(那是本文件的錯)。
交付副本時檔名加前綴:cats-inbox_來源接入指南_v1.0.md(憲法 A.4)。

0. 先看這三條(它們都不會有錯誤訊息)

#規則違反時會怎樣
1recipient_sub 填 Keycloak 的 sub(UUID),不是 email、不是帳號名本服務回 400。若回的是 201,那則通知就只有 sub 相符的那個人看得到 —— 收件匣以 sub 比對
2每個事件一把 Idempotency-Key,重送時沿用同一把每次重送都換新 key → 收件人看到重複的通知;不同事件共用一把 key → 422(若我們回放而不報錯,第二則會默默消失 —— 所以我們報錯)
3只推純文字;連結只能是同站HTML 會被原樣跳脫顯示(看到 <b> 字面);外部連結 400 拒收 —— 站內通知是現成的釣魚載具

1. 開通流程(誰做什麼)

步誰做什麼產出
①來源系統 + BennyDI-4 立案:決定哪些事件要推、推給誰事件清單
②portal依契約 §11 建 S2S client <client_id>-sa(client_credentials);掛 optional client scope notification:push(內含 audience mapper → cats-inbox)client_id + secret(🔴 走安全管道,不進聊天、git、issue、CI log)
③cats-inbox 管理員/inbox/admin/sources 登記 azp = 上面的 client_id,標籤填系統名(例「TRF 系統」,≤ 32 字,不得是人名)來源登記
④來源系統依本指南 §2–§5 實作—
⑤雙方跑 §7 冒煙,結果寫進 cats-inbox 任務 T14b 的 dev-log冒煙紀錄

⚠ 順序:③ 沒做之前,就算 ② 的 token 完全正確也是 403 source_not_registered —— 那是預期中的,不是 bug。

2. 取 token(client_credentials)

項目值
token 端點(同一台 VM、在 cats-edge 上的容器)http://keycloak:8080/auth/realms/sporton/protocol/openid-connect/token
token 端點(其他位置)https://catsapp.sporton.com.tw/auth/realms/sporton/protocol/openid-connect/token
grant_typeclient_credentials
scopenotification:push(🔴 必須明確要求 —— 它是 optional scope,不要求就不會出現在 token 裡)
client 認證client_id + client_secret(form body 或 HTTP Basic)

🔴 token 要快取,不要每推一次就換一張:access token 效期內重用,到期前 60 秒再換。
每次都換會把 IdP 變成你們推送路徑上的熱路徑相依(契約 §11.6 反對),IdP 慢一次,你們的每一則通知都跟著慢。

⚠ 容器內走內部位址換來的 token,iss 仍是對外網址 —— 這是對的(契約 §2.4),本服務驗的就是對外那個值。

3. 呼叫推送 API

項目值
方法與路徑POST /inbox/api/v1/notifications
位址(同一台 VM、在 cats-edge 上的容器)http://cats-inbox-api:8080/inbox/api/v1/notifications
位址(經統一入口)https://catsapp.sporton.com.tw/inbox/api/v1/notifications —— ⚠ cats-inbox T11b(gateway 路由啟用)完成後才通

⚠ 走內部位址不代表可以不帶 token —— 本服務完全不看來源位址(契約 §11.5:「內網不是身分」)。

3.1 標頭(三個都必帶)

標頭內容規則
AuthorizationBearer <access token>§2 換來的那張
X-User-Id觸發這個事件的人的 sub(UUID)🔴 portal 加嚴條件:必帶、必驗。不得是你們 service account 自己;不得省略當成「系統發出」—— 稽核鏈靠它
Idempotency-Key這個事件的唯一識別1–128 個可見 ASCII 字元(不含空白);逐字比對(含引號、大小寫)
Content-Typeapplication/jsonbody 必須是 UTF-8 的 JSON 物件,≤ 256 KiB

Idempotency-Key 怎麼產生: 用事件本身的識別組出來,例 trf:returned:TRF-2026-00123:v3。
🔴 不要用時間戳或亂數(重送時會變 → 重複通知);不要用固定字串(不同事件撞 key → 422)。
同一把 key 在 24 小時內重送 = 回放第一次的結果;滿 24 小時之後同一把 key 會被當成新的一則。

⚠ 待 portal 確認的一點:沒有人觸發的事件(排程、批次)要填誰當 X-User-Id,核定規格沒有明講。
本服務的提議:填該排程的負責人的 sub,並在你們的 log 記下「排程觸發」—— 仍不得填 service account 自己。T14b 動工前定案。

3.2 body

{
  "recipient_sub": "0b5a7c2e-1f3d-4e8a-9b6c-2d4e6f8a0b1c",
  "subject": "TRF-2026-00123 已退回",
  "body": "審核意見:附件缺第 3 頁。請補件後重送。",
  "action_url": "/compliance/trf/2026-00123"
}
欄位必填規則
recipient_sub✅收件人的 Keycloak sub(UUID;大小寫不拘,存成小寫)。不必先登入過站內信
subject✅純文字,1–255 字
body✅純文字,1–20000 字。換行會保留;HTML 不會被解讀(跳脫顯示)
action_url—「前往處理」按鈕的連結。只接受同站:/ 開頭的相對路徑,或 https://catsapp.sporton.com.tw/ 開頭。//x、/\x、javascript:、外部網址一律 400

🔴 不要送 source_app、category、sender_sub —— 送了也會被忽略。
收件匣上顯示的來源標籤一律是 §1 ③ 登記的那個,由你們的 client 身分推導,不採信 body(能自稱來源 = 能冒充任何系統)。

一次呼叫只推給一個人。要推給多人,就逐人呼叫,每人一把 key(例 …:v3:<收件人 sub>)。

4. 回應與錯誤碼

成功:

狀態意思body
201建立了一則新通知{"id": "<訊息 id>"}
20024 小時內同一把 key、同內容的重送:回放第一次的結果,沒有新增{"id": "<第一次的 id>"},並帶標頭 Idempotent-Replayed: true

失敗(body 一律是 {"error": "<代碼>"},細節只在本服務的 log 裡):

狀態error意思你們該做什麼可重試?
401missing_token沒帶 Authorization: Bearer帶上 token修正後
401invalid_tokentoken 驗不過:過期、aud 不含 cats-inbox、不是 access token、簽章/iss 不對換一張新 token 重試一次;還是 401 就檢查 §2 的 scope 與 client換 token 後一次
403insufficient_scopetoken 有效但沒有 notification:push換 token 時要求 scope=notification:push;還是沒有 → 找 portal 掛 optional scope❌
403source_not_registered你們的 client_id 沒登記找 cats-inbox 管理員做 §1 ③❌
403source_disabled你們的來源被停用了找 cats-inbox 管理員(通常是因為推送異常而被暫停)❌
400missing_x_user_id / invalid_x_user_id / x_user_id_is_callerX-User-Id 缺、不是 UUID、或是你們自己的 service account見 §3.1修正後
400missing_idempotency_key / invalid_idempotency_keykey 缺或含空白/非 ASCII/超過 128 字見 §3.1修正後
400invalid_json / invalid_payload / payload_too_largebody 不是 JSON 物件、欄位型別不對、超過 256 KiB見 §3.2修正後
400invalid_recipient_sub收件人不是 UUID(常見:填了 email 或帳號名)改填 sub修正後
400empty_field / field_too_long主旨或內容空白/超長見 §3.2修正後
400action_url_*連結不是同站見 §3.2修正後
422idempotency_key_reused這把 key 24 小時內已用於內容不同的請求🔴 這是你們的 bug:不同事件共用了 key。修 key 的產生方式,不要換一把新 key 硬推過去❌
5xx / 逾時—本服務或網路異常同一把 key 重試✅

5. 重試規則

  1. 只對 5xx 與網路錯誤重試,最多 2 次,指數退避(例:1 秒、4 秒)—— 契約 §11.6。
  2. 重試一律沿用同一把 Idempotency-Key:第一次其實成功、只是回應沒送到的話,重試會拿到 200 回放而不是第二則通知。
  3. 4xx 不重試(401 invalid_token 例外:換一張新 token 重試一次)。4xx 的意思是「這個請求本身有問題」,原樣重送只會再錯一次。
  4. 超過 24 小時才補送的同一事件,會被當成新的一則(寧可重複一次,也不要靜默丟掉)。

6. 本服務這一側保證的事

保證怎麼做到的
同一則不會因為重送而出現兩次(你們的 client_id, key) 唯一約束;並行的同 key 請求也只會留下一則
你們的 key 不會跟別的系統撞key 以呼叫方為範圍
通知內容不進 log本服務只記 client_id、觸發者、收件人的 sub 與訊息 id
沒登入過站內信的人也收得到收件人不需要先存在;他第一次登入就會看到
停用一個來源是即時的每一次請求都查登記表,不快取

7. 冒煙清單(T14b 用)

在你們的容器裡跑(它在 cats-edge 上,與正式呼叫的網路路徑相同)。
🔴 secret 從容器既有的環境變數讀,不要貼進指令、不要印出來 —— 本專案 2026-08-28 發生過一次 secret 印在畫面上而必須輪替的事故。

🖥️ 在哪執行: Cats VM(ssh 進去)· 工作目錄 任意
🏷️ 動到誰的東西: 來源系統(在它的容器裡執行;把 <來源容器> 與兩個環境變數名換成你們的)

docker exec -i <來源容器> python - <<'PY'
import json, os, urllib.error, urllib.parse, urllib.request

TOKEN_URL = "http://keycloak:8080/auth/realms/sporton/protocol/openid-connect/token"
PUSH_URL = "http://cats-inbox-api:8080/inbox/api/v1/notifications"
form = urllib.parse.urlencode({
    "grant_type": "client_credentials",
    "client_id": os.environ["NOTIFY_CLIENT_ID"],          # ← 換成你們的變數名
    "client_secret": os.environ["NOTIFY_CLIENT_SECRET"],  # ← 同上;🔴 不要印出來
    "scope": "notification:push",
}).encode()
token = json.load(urllib.request.urlopen(urllib.request.Request(TOKEN_URL, data=form)))["access_token"]

def push(key, subject):
    req = urllib.request.Request(PUSH_URL, method="POST", data=json.dumps({
        "recipient_sub": os.environ["SMOKE_RECIPIENT_SUB"],   # ← 冒煙收件人的 sub
        "subject": subject, "body": "cats-inbox 冒煙測試,可忽略。",
    }).encode(), headers={
        "Authorization": f"Bearer {token}", "Content-Type": "application/json",
        "X-User-Id": os.environ["SMOKE_ACTOR_SUB"],           # ← 觸發者的 sub(不是 service account)
        "Idempotency-Key": key,
    })
    try:
        with urllib.request.urlopen(req) as r:
            return r.status, json.load(r), r.headers.get("Idempotent-Replayed")
    except urllib.error.HTTPError as e:
        return e.code, json.load(e), None

print("① 首次        ", push("smoke:1", "冒煙 A"))   # 預期 201
print("② 同 key 重送  ", push("smoke:1", "冒煙 A"))   # 預期 200 + 'true',id 與 ① 相同
print("③ 同 key 改內容", push("smoke:1", "冒煙 B"))   # 預期 422 idempotency_key_reused
PY

怎麼知道成功了:

步預期不是預期時
①(201, {'id': '…'}, None)403 source_not_registered → §1 ③ 還沒做;403 insufficient_scope → token 沒要 scope 或 portal 沒掛;401 → 見 §4
②(200, {'id': <與 ① 相同>}, 'true')201 且 id 不同 → 去重沒生效,停下來回報 cats-inbox
③(422, {'error': 'idempotency_key_reused'}, None)200 → 不同內容被當成重送,停下來回報
④收件人登入 /inbox/,看得到「冒煙 A」,來源標籤是 §1 ③ 登記的名字看不到 → 核對 SMOKE_RECIPIENT_SUB 是不是他的 sub(不是 email)

⚠ 冒煙產生的「冒煙 A」會留在收件人的收件匣裡(本服務沒有刪除 API)—— 收件人請選自己人。

8. 常見錯誤對照(位置 / 原因 / 修法)

位置症狀原因修法
推送回應403 insufficient_scope,而 token 換得到換 token 時沒帶 scope=notification:push(它是 optional scope)換 token 的 form 加 scope=notification:push
推送回應401 invalid_token,token 剛換的aud 不含 cats-inbox(portal 的 audience mapper 沒掛在那個 scope 上),或拿成了 id_token把 token 貼到 jwt 解碼工具看 aud 與 typ(應為 Bearer)—— 🔴 用離線工具,不要貼到網站
收件匣推送回 201,收件人說沒看到recipient_sub 填成別人的 sub用收件人本人的 sub;本服務已擋掉「不是 UUID」的情況,擋不住「是 UUID 但不是他」
收件匣同一件事出現兩次重試時換了 key,或超過 24 小時才補送重試沿用同一把 key(§5)
推送回應大量 422key 由時間戳/固定字串產生,不同事件撞在一起key 改由事件識別組成(§3.1)
