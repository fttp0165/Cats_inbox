0. TL;DR(給 portal 的五句話)

  1. 申請 confidential client cats-inbox(PKCE S256 疊加),redirect URI 一條、完整比對、含 /inbox/ 前綴。
  2. session 形態聲明:cookie / 伺服器 session → 依 §10.3 承擔 front-channel logout 端點義務,路徑已定。
  3. claims 只要 name(用途受限,見〈參〉);不申請 email、不申請 groups。
  4. 隨函一件:開通政策偏離申請——「讀自己的收件匣」請准首登自動授 reader,寄信與發公告維持 deny-by-default 手動開通(詳〈伍〉)。未核可前照契約全 deny,不先斬後奏。
  5. 另預告兩件、本次都不請求:/inbox/ 閘道路由(〈肆〉)、S2S 推送驗證規格(〈陸〉,我方為第三個 S2S 需求且角色相反)。

本系統為 FastAPI + Jinja2 伺服器端算繪,後端有一條路由 GET /inbox/oidc/callback/ 接 IdP callback、拿 code 換 token、簽發自己的 HttpOnly cookie session → 落第一列 confidential。前端無 JS 執行 OIDC 流程、不持有 token(§4.10:token 不進 localStorage),非第三列「SPA + 自家 API 後端」型。

我方已注意 §5.1 的警告:第三列誤設成 confidential 建立時不會報錯、回讀驗證也會過,直到第一次登入才在 token 端點失敗(portal-admin 前例放了三天沒人發現)。本系統確認是第一列,故請以 confidential 建立。

伍、開通政策偏離申請:「讀自己的收件匣」請准首登自動授 reader

一、申請內容

動作申請的授權方式
讀自己的收件匣、標自己的訊息已讀、看有效公告首登自動授 reader 角色 ←(這是偏離)
寄人對人站內信(sender)維持 deny-by-default、管理後台手動開通
發布公告(announcer)維持 deny-by-default、管理後台手動開通
管理(派角色、清快取)(admin)維持 deny-by-default;bootstrap 清單 + 手動開通

偏離的是哪一條: §4.3/§4.4「首登建本地 user(零角色)→ 所有業務功能 403 待開通」中,僅「讀自己收件匣」這一項。其餘一字不動。

二、為什麼提這個偏離

  1. 通知中心的可用性等於「送得到」。 逐人手動開通的結果是:系統推了通知、使用者收不到,而且畫面上一切正常——他只看到待開通頁。通知系統最糟的失效模式不是報錯,是安靜地沒送到。
  2. 這個代價貴方已經記載過。 §4.2a D7-7 裁決文自陳:deny-by-default 之下「上線首日會有一批同時湧入的待開通帳號,ADMIN 處理完之前那些人看到 403——功能正確,體感像壞了」。對一般業務系統這是可承受的;對全平台的通知管道,它會讓每一個接進來的來源系統一起看起來壞掉。
  3. 這裡沒有「別人的資料」可被越權讀取。 reader 能讀的集合恆等於 recipient_sub == 自己。它不是「先給權限、之後收回」,而是這個角色的可及範圍在定義上就只有本人。
  4. 平台規模參考:PLM 正式環境 206 位使用者(貴方憲法 v1.7 更正值)。逐人開通通知讀取權,行政成本與其換得的安全性不相稱。

三、風險與緩解(誠實列出,不粉飾)

風險緩解
自助註冊帳號(限 @sporton.com.tw)一登入就有收件匣他只會看到空的收件匣——訊息要有人推給他才存在。寄信與發公告仍是手動開通,濫發路徑沒有打開
「註冊 ≠ 授權」原則被稀釋本申請不觸碰任何業務系統的授權;inbox 的讀取範圍恆為本人
日後被援引為先例我方同意將核可範圍寫死在「自我範圍資料的讀取」;任何跨人可見的功能(寄信、公告、管理)一律回到 deny-by-default
停用能力(§1.1 / D9=B)保留:reader 可由我方後台單獨停用,不依賴 IdP 帳號狀態

  • upload-program 的「未登入開首頁可見說明性落地頁」是貴方唯一經核准的偏離(裁決見 DOCS/回覆_upload-program_SSO接入申請_20260729.md),程序可循:申請書 → 裁決文件 → 契約 §6 專屬條款登記。
