4. 三問的答覆(portal 回覆函〈肆〉)

Q1 登出後實際導向哪一頁?

答:https://catsapp.sporton.com.tw/inbox/(client 已登記的兩值之一,不需重跑腳本)。

理由:我方沒有獨立的「已登出」頁——收件匣本身在未登入時就是導向 IdP 登入頁,故登出後回 /inbox/ 的行為是「回到入口 → 被導去登入頁」,語意正確且少一個要維護的頁面。/inbox/logged-out/ 這個登記值保留備用,若日後要顯示「你已登出」的說明頁再啟用(登記值已在,不必再改 client)。

🔴 front-channel 端點路徑確認:/inbox/oidc/frontchannel-logout,無結尾斜線,與 client 登記值逐字相同(§10.3a)。T06 實作時 FastAPI 的 route 必須寫成完全一樣的字串。

Q2 source_app 由 service client 身分推導的具體對應方式?

答:資料庫表 source_app,以 azp(呼叫方 client_id)為主鍵。

選項取捨採用
程式內靜態 dict最簡單,但新增來源要改程式 + 重新部署❌
DB 表(azp → 顯示標籤 + 啟用旗標)新增來源=管理後台加一列;可停用單一來源而不動程式✅
Keycloak client attribute對應留在 IdP,但我方每次推送都要查 Keycloak,把 IdP 變成熱路徑相依(§11.6 明文反對)❌

未登記的 azp → 403(deny-by-default,§11.5 第 3 條),不 fallback 成「未知來源」——通知顯示來源標籤,一個能自稱來源的呼叫方就是釣魚載具。

Q3 Idempotency-Key 的保留窗口?

答:24 小時;超過窗口的同 key 重送視為新訊息。

理由:

  • 下限由重試策略決定:§11.6 規定重試 ≤2 次 + 指數退避,實際重送間隔是秒到分鐘級。24 小時遠大於它,涵蓋「呼叫方排程整批重跑」這種最長的合理重送。
  • 上限由儲存決定:去重表只存 (azp, key, message_id, created_at),24 小時的量級是「一天的推送筆數」,可用單一 DELETE WHERE created_at < now() - 24h 的每日清理搞定,不需要額外基礎設施。
  • 超過窗口視為新訊息而非拒收:拒收會讓一個月後的重跑靜默失敗,而通知沒送到是這個系統最糟的失效模式。寧可重複一次,也不要靜默丟掉。

⚠ 誠實標註:24 小時是推理出來的值,不是實測。上線後若出現「同一事件隔天重複出現在收件匣」,窗口要往上調——這一句寫進 T14 的遺留問題。
